## 1단계에서 한 것

- SP v0.4.72 를 복사해 객체 · 온톨로지 계열 백엔드 모듈 13 · 확장 2 · 화면 모듈 11 을 걷어냈다.
  마이그레이션은 `0001_initial` 하나(작업 결과 요약 함수 `sp_job_brief` 포함) — `alembic check` 가
  모델과 차이 없음을 확인한다.
- 이름 `datarelay` · 오류 접두사 `DRL` · 포트 8080/8081/8082 · Vite 5250 · PAT 범위 `relay:write`.
- 뜻으로 찾기(pgvector · bge-m3) 장치를 걷어냈다 — 개발 PC 에 `sudo` 로 pgvector 를 깔 일이 없다.
- `relay_core`: 미러(증분 · 전량 · 부재 대조) · 변환(`sp_table.convert` 그대로) · 출력 비교(바뀐 줄 ·
  무덤, 결과가 `sp_pipeline.validate` 통과).
- 사이드바에 「중계」 묶음(연결 지도 · 파이프라인 · 원천 시스템 · 대상 인스턴스)을 미구현 자리로.

## 2단계에서 한 것

- PLM 은 **API 에서 직접** 받는다(사용자 결정, 2026-11-05).
- `relay_core/adapters/rest.py` — 쪽 넘김(page · offset · cursor) · `since` 증분 · 삭제 표시 · 중첩 펴기
  (`columns`) · 인증(bearer · header · basic) · 5xx 만 다시 묻기.
- `definition.py`(`relay-pipeline/1` — 비밀은 `token_env` 로만) · `state.py`(작업 폴더: 미러 · 워터마크 ·
  지난번 적용된 출력 · 대기 계획) · `submit.py`(미리보기는 `sp_pipeline.cmd_preview`, **적용은
  `POST /api/jobs/{id}/apply`** — SP 의 계획에 `applied_by` 가 찬다) · `runner.py` · `cli.py`.
- 대기 중인 계획과 같은 것은 다시 올리지 않는다(`waiting`) — 사람이 며칠 안 눌러도 계획이 쌓이지 않는다.
- 개발 PC 시험: 샘플 PLM API(8088) → SP 시험 인스턴스 「자주검증 Datahub(시험)」(8087, 별도 DB). 결과는
  [devtools/README.md](../devtools/README.md).

### 시험에서 알게 된 것

- **잠금은 타입에 걸린다**(`ObjectType.managed_by`). `source: plm` 묶음으로 **정의를** 넣어야 잠긴다 —
  `source` 없는 정의 가져오기로 넣은 타입은 사람이 고칠 수 있었다. 진짜 Datahub 에서 PLM 정보를 담는 타입의
  정의가 어떻게 들어가 있는지 확인해야 한다(아래 ② — **운영의 slug 는 `plm_` 으로 시작하지 않는 것도 있다**). 정의를 잠그는 일은 한 번 · 시스템 관리자 · `ontology:write` 이고,
  relay 의 평소 토큰은 `objects:write` 만 있으면 된다.
- **잠그기 전에 사람이 고친 값은 relay 가 모른다** — relay 는 자기 출력끼리 견주므로 원천이 안 바뀐 행은
  다시 안 보낸다. 대상의 지금 값과 견주는 대조(주 1회 · 코어 API 로)를 4단계에 둔다.
- 워터마크를 원천이 안 주면 받은 행의 `updated_at` 최댓값을 쓴다 — 원천의 `updated_since` 가 「이상」
  이면 경계 행이 한 번 더 올 뿐이라 해가 없고, 「초과」 면 같은 시각에 바뀐 행을 놓칠 수 있다. 진짜
  PLM API 가 어느 쪽인지, `as_of` 같은 값을 주는지 확인한다(`watermark_path`).

## 3 · 4단계에서 한 것

- **OData 어댑터**(`relay_core/adapters/odata.py`) — PLM 응답이 OData 라는 것까지 알고 만들었다(2026-11-05).
  v4 · v2 봉투, 서버가 주는 다음 쪽(`nextLink` · `__next`) · 없으면 `$skip`, 증분 `$filter`(v2 는
  `datetime'…'`), v2 의 `/Date()/`, `$expand` 를 점으로 펴기. 삭제 칸이 없으면 증분 `full_every` 번마다
  전량을 받아 부재 대조. 샘플 PLM 도 OData v4 로 답한다.
- **연결 지도 API**(`/api/relay/map`) · **파이프라인 상세**(필드 계보 · 대상 정의와 대조 · 상태 · 이력 · 작업) ·
  **실행 · 적용을 작업으로**(`relay_run` · `relay_apply`, 시스템 관리자) · 홈 「남은 일」(적용 대기 · 멈춤).
  화면은 `frontend/src/modules/relay/`.
- **레시피의 판**(`relay_recipes`) — 초안 · 시험(미러에 돌려 「켜면 바뀌는 것」 을 보임, 대상엔 안 보냄) ·
  켜기(**화면의 사람만** — 토큰이면 `RELAY-0007`). 켜진 판이 실행 · 지도 · 상세에 쓰인다.
- **MCP 서버**(`mcp_server/`, 8082) — 사용자 PAT 를 넘긴다. 보기(지도 · 상세 · 원천 표본 · 대상 정의 ·
  레시피) · 짓기(초안 · 시험) · 미리 보기 실행. **켜기 · 적용 도구는 없다.** Claude Desktop 으로 붙는다
  (허용, 2026-11-05 — 엔터프라이즈). 진짜 MCP 클라이언트로 초안 → 시험 → 켜기 거절까지 돌려 봤다.
- **서버 준비** — SIF 에 `vendor/` 를 담고, 중계 폴더(`<DATA_DIR>/relay` — 이중화면 공용, 정의는
  `pipelines/`, 상태는 `work/`)를 API · 워커 · 타이머에 잇는다. 타이머(5분마다)가 일정(`schedule`:
  `daily_at` · `every_minutes`)이 된 파이프라인을 작업으로 넣는다(`scripts/relay_due.py`). 배포 묶음에서
  정제 도구 키트 · 지표 타이머를 뺐다. CI 는 `mcp_server` · `devtools` 를 함께 본다.
- **`relay check <정의>`** — relay 를 둘 서버에서 원천(한 줄만)과 대상(slug · 판 · 토큰 주인 · 시스템
  관리자인가)에 닿는지 본다. 아무것도 안 바꾼다.

### 시험에서 고친 것

- **빈 값은 「바뀜」 이 아니다 · 비워진 칸은 `\null` 로** — SP 에서 `null` · 빈 값은 「안 보냄」 이다. 새
  칸이 대부분 빈 레시피가 「모델 10개 바뀜」 으로 셌고(실제 1개), 거꾸로 원천에서 값이 지워지면 `null` 을
  보내 **옛 값이 대상에 남을 뻔했다.** 비교는 빈 값을 빼고, 값이 있다 사라진 칸은 `\null` 로 보낸다.
- **API 와 워커를 같은 순간에 띄우면 워커가 죽었다**(틀에서 온 것) — 둘이 같은 이름의 쓰기 확인
  파일(`.write-probe`)을 만들고 지웠다. 이름에 프로세스 번호를 붙였다.

## 4a 에서 한 것 — 어댑터 형식 · 정의의 판

MES 가 무엇으로 줄지 아직 모른다(2026-11-05). 그래서 흔한 형식을 다 받게 하고, **붙이는 일(어댑터 설정)을
AI 가 MCP 로 하게** 했다 — 형식을 아는 날 코드가 아니라 정의 하나를 짓는다.

- **어댑터 넷** — `rest` · `odata` 에 더해 `file`(CSV · TSV · Excel · JSON, 로컬 glob 이면 가장 늦게 바뀐 것 ·
  URL, 인코딩 자동 — UTF-8 · CP949, 머리글 줄 · 시트), `xml`(XPath 로 행 · 칸, 속성 · 여러 값, SOAP 봉투에
  `{since}` · `{page}`, Fault 면 멈춤, **바깥 엔티티를 따라가지 않는다**). 어댑터마다 `probe` · `discover`.
  처음엔 `sql`(DB 뷰 직접 읽기 · Oracle · MSSQL 드라이버)까지 다섯이었다 — **2026-11-05 걷어냈다**: 원천은 API ·
  파일 · 공유 폴더로만 받는다. API 없는 DB 에 바로 붙을 일도 권한도 없다(MES 도 API 로).
- **정의의 판**(`relay_definitions`) — 레시피의 판과 같은 길: 초안 · 시험 · 켜기(사람만, 토큰이면
  `RELAY-0014`). 켜진 판이 같은 slug 의 정의 파일을 이긴다. 켜진 판이 없는 새 slug 는 지도에
  「초안(꺼짐)」 으로 서고 돌지 않는다(`RELAY-0015`). DB 의 정의에는 `recipe` 칸이 없다 — 레시피는 레시피 판(없으면
  같은 slug 의 정의 파일 것).
- **정의 시험**은 원천을 전량 받아 보고(저장 안 함) · 대상(닿나 · 토큰 · 레시피가 만드는 타입이 있나 · 잠금 주인) ·
  레시피로 바꿔 보기(행 수 · 미해결 · 「켜면 보낼 것」)까지 한 번에 한다. **같은 대상의 같은 타입을 다른
  파이프라인이 이미 채우면** 그렇다고 말한다 — 두 길로 채우면 서로가 안 보낸 것을 무덤으로 낸다.
- **MCP 도구 여섯** — `adapter_kinds`(칸 · 기본값 · 설명을 코드의 설명 글에서) · `source_discover`(키 · 열을
  몰라도, 칸의 자리 · 보기 값 · 열 이름 제안, OData 면 `$metadata` 의 엔티티 셋) · `pipeline_definitions` ·
  `pipeline_definition_get` · `pipeline_draft_save` · `pipeline_test`. 안내 `get_guide('adapter')` ·
  `get_guide('types')`(대상에 타입이 없으면 — 대상 SP 의 MCP 로 `source` 를 단 묶음, 적용은 사람).
- **울타리**(`app/modules/relay/guard.py`) — 탐색 · 정의 시험은 서버가 바깥에 닿는 일이라:
  주소는 `RELAY_SOURCE_HOSTS` 또는 켜진 정의의 주소만(비밀이 엉뚱한 곳으로 안 나가게), 로컬 파일은
  `RELAY_FILE_ROOTS` 안만(어댑터가 실제로 고른 파일을 링크 끝까지 다시 본다 — 도는 길에도 선다),
  `token_env` 로 플랫폼 자신의 설정(`DATABASE_URL` · `JWT_SECRET` …)을 못 가리킨다, 정의 어디에도 비밀 칸 ·
  비밀 같은 값(주소 속 비밀번호 · `Bearer …`)이 없어야 저장된다. 운영 파일 폴더는 `<DATA_DIR>/relay/drop`.
- **공유 폴더(SMB)** — 파일 원천의 `location` 에 `smb://<서버>/<공유>/<폴더>/lots-*.csv`. 서버에 마운트하지 않고
  바로 읽는다(`smbprotocol`, SMB2/3 · NTLM). 계정은 `auth.user`, 비밀번호는 `auth.token_env`. 서버 주소는
  `RELAY_SOURCE_HOSTS` 울타리를 똑같이 지난다. 가짜 공유 폴더로만 시험했다 — **진짜 사내 공유 폴더에는 아직
  붙여 보지 않았다**(첫 연결 때 445 포트 · 계정 확인).
- **초안 버리기**(정의 · 레시피, 초안만 — 토큰도 된다, `RELAY-0017`) · **시험용 상한**(`RELAY_TRIAL_ROWS`, 기본
  5,000줄 — 넘으면 앞만 받고 「켜면 보낼 것」 은 세지 않는다).
- 옛 Excel(`.xls`)은 받지 않는다(정함, 2026-11-05).
- 진짜 MCP 클라이언트로 돌려 봤다(2026-11-05): OData `$metadata` 탐색 → REST 정의 초안 → 레시피 초안 → 정의 시험
  (객체 17 · 미해결 0, 대상 타입 넷 다 `managed_by=plm`) · `/etc/passwd` · 바깥 주소 · 정의 속 토큰 · 토큰으로
  켜기가 모두 거절됐다. 그 초안(`mock-plm-rest-trial`)은 개발 DB 에 남아 지도에 「초안」 으로 선다.

## 4b 에서 한 것 — 자동 적용

- 정의의 `auto_apply`(`true` 또는 `{"after_manual": 3, "max_changes": 500, "allow_gone": false}`) —
  `relay_core/autoapply.py`. **타이머가 돌린 실행에만** 쓴다(사람의 「지금 실행」 · MCP 의 실행은 계획만 올린다).
- 기준을 모두 넘으면 같은 작업 안에서 적용하고 이력에 `applied`(`by: auto`), 못 넘으면 `auto_skipped` 와 까닭을
  남기고 계획은 사람을 기다린다(홈 「남은 일」). 자동으로 적용한 것은 「사람이 적용한 횟수」 에 세지 않는다.
- 켜는 길은 정의 판뿐이라 **사람이 정한다** — AI 안내는 「사람이 말하지 않았으면 적지 않는다」.

## 4c 에서 한 것 — 대조

- `relay_core/reconcile.py` — 대상 SP 의 목록(`GET /api/objects/{타입}`, 사용 중지 포함 · 쪽 200)을
  지난번 **적용된** 출력(기준)과 견준다. 갈래는 넷: **빠짐**(대상에 없음) · **안 씀**(대상에서 사용 중지) ·
  **다름**(칸 값이 다름 — 칸 이름까지) · **대상에만**(기준에 없는데 살아 있음). 빈 칸은 「안 보냄」 이라
  견주지 않는다. 값은 모양을 맞춰 견준다(숫자 `12.50` = `12.5` · 날짜 · 참 거짓 · `;` 여러 값). 참조 칸은
  대상이 id 로 주므로, 같은 대조에서 받은 객체면 그 식별자로, 아니면 상대의 이름으로 견주고, 둘 다 아니면
  「확인 못 함」 으로 센다(어긋남이 아니다). **읽기만 한다** — 내보내기 API(시스템 관리자 전용)는 쓰지 않는다.
- **보정 계획**(`resync`) — 어긋난 줄을 기준 그대로 다시 보내는 미리보기. 안 씀은 `status: active` 로
  되살리고, 대상에만은 **그 타입을 이 원천이 잠갔을 때만**(`managed_by == source`) 무덤(사용 중지)으로 싣는다.
  다시 보내는 객체에 닿는 기준의 선을 함께 싣는다(대상에 있으면 「그대로」). 평소 계획과 같은 길이라 대상의
  검토함에 뜨고 적용은 사람이 한다. 적용을 기다리는 계획이 있으면 올리지 않는다. 계획에 `origin: reconcile`
  이 남고, **적용하면 같은 작업이 다시 대조**해 홈의 「어긋남」 이 바로 풀린다. 기준은 그대로다(원천이 안
  바뀌었다).
- 작업 `relay_reconcile`(시스템 관리자 · 타이머) · `POST /api/relay/pipelines/{slug}/reconcile {plan}` ·
  `GET …/reconcile`(보고서 전부, 상세는 본보기 20개) · 지도 노드의 `drift` · 홈 「대상과 어긋난
  파이프라인(대조)」 · MCP `pipeline_reconcile` · `pipeline_reconcile_report` · `get_guide('reconcile')` ·
  CLI `relay reconcile <정의> [--plan]`(어긋나면 끝값 1).
- 일정 — `RELAY_RECONCILE_DAYS`(기본 7, 0 이면 화면 · MCP 에서만) · `RELAY_RECONCILE_AT`(기본 `03:00`). 적용한
  것이 있는 파이프라인만, 첫 적용 뒤 처음 맞는 그 시각에, 그 뒤로는 그 날수마다.
- 선은 아직 따로 견주지 않는다 — SP API 가 관계 종류마다의 선 목록을 주지 않는다(보정 계획이 닿는 선을
  다시 보내는 것으로 메운다).

## 무인 운영 준비(2026-11-05)

- **알림**(`app/modules/relay/alerts.py`) — 타이머가 밤에 돌린 실행 · 대조는 시킨 사람이 없어 작업 알림이 아무에게도
  안 갔다. 이제 실행 갈래(실패 · 멈춤 · 정상)와 대조 갈래(같음 · 어긋남 · 대조 실패)의 상태가 **바뀔 때만** 시스템
  관리자 모두에게 알린다 — 같은 실패가 밤마다 되풀이돼도 하나, 다시 되면 「복구」 · 「일치」 하나. 지난번 상태는
  `work/<slug>/alerts.json`(이중화면 공용 · 자문 잠금). 시킨 사람은 빼고 보낸다. 실패한 작업은 워커가 롤백한 뒤
  다른 세션에서 「실패」 를 적으므로, 작업 틀에 **끝난 뒤 자리**(`Kind.after` — `settle` 에서, 오류는 결과를 안
  바꾼다)를 두고 거기서 알린다. 개발 서버에서: 샘플 PLM 을 내리고 타이머처럼 두 번 실행 → 「실행 실패」 하나,
  다시 띄우고 한 번 → 「실행 복구」 하나. **계획 갈래**도 본다 — 적용할 수 있는 계획이 없다가 생기면 「적용
  대기」 하나(자동 적용은 기본이 꺼져 있어 밤의 실행이 올린 계획은 사람을 기다린다 — 홈의 숫자만으로는 누가
  열기 전까지 모른다). 적용돼 없어지는 것은 알리지 않는다. 오류가 있는 계획은 「실행 멈춤」 이 대신 말한다.
  **할 것이 없던 적용**(대기 계획 없음)은 실행 갈래를 바꾸지 않는다 — 실패한 실행 뒤에 누른 「적용」 이 「실행
  복구」 로 읽혔다(2026-11-06 개발 서버: 대상 SP 의 워커가 멈춰 실행이 실패한 뒤).
- **백업이 중계 폴더도**(`backup.sh -r`, 기본 `.env` 옆의 `relay/`) — `pipelines/` 전부와 `work/` 의 이어 돌 몫(상태 ·
  미러 · 대조 보고서 · 알림 상태 · 기준 출력 하나)을 `relay/relay-<시각>.tar.gz` 로, 덤프와 같은 세대.
  `restore.sh -R` 이 덤프와 같은 시각의 묶음을 되돌리고, `-R` 이 없으면 읽히는지만 본다. 개발 DB 로 진짜
  `pg_dump` → 확인용 DB 복원 · 중계 폴더 복원까지 돌렸다(표 23 · 중계 파일 15).
- **틀에서 남은 것 정리** — 읽는 곳이 없는 설정 19개(지표 · 그래프 지도 · 데이터 소스 · 무덤 보관 · 사진 zip …)와
  `.env` 예시의 그 줄들, 이중화 nginx 조각의 사진 zip 경로(없는 경로가 2GB 를 받던 문), 없는 기능의 알림 종류
  7개, CI 의 pgvector 이미지(→ `postgres:16`), 504 · 507 안내의 「지표로 미리 세어 두세요」 · SPARQL. 옛 `.env` 에
  지운 이름이 남아 있어도 앱은 뜬다(설정은 모르는 칸을 무시한다).
- **작업 폴더 정리**(`Workdir.prune`, `RELAY_KEEP_RUNS` 기본 10) — 실행마다 `runs/` · `sends/` · `work/` 가 하나씩
  늘고 지우는 곳이 없었다. 실행 · 적용 · 보정 계획 작업이 끝날 때 폴더마다 최근 10개와 상태가 가리키는 것(기준
  출력, 대기 계획의 출력 · 묶음, 그 실행의 원천 표)만 남긴다. 실행 시각 이름 모양만 지운다(시험의 임시 폴더 ·
  사람이 둔 파일은 그대로). 가장 최근 것이 남으므로 「멈춤」 안내의 `unresolved.json` 도, 이중화의 다른 워커가
  만드는 중인 폴더도 지워지지 않는다. 정리가 실패해도 작업은 실패가 아니다.

## 운영 첫 연결 대비(2026-11-06)

  백업에서 되살린 폴더) 지금 레시피 · 지금 미러로 찾고 그렇다고 적는다. 정리(`prune`)는 `work/` 를 실행 시각으로
  묶어 센다. 식별자를 참조 대조 · 해석기 · 날짜로 정한 타입은 원천 행을 다 못 찾아 첫 행만 보인다.

  이름 · 레시피에 없는 타입은 막는다. 저장한 초안은 목록의 「시험」 → 「사용」 으로 간다(작성 경로 「화면」).

  화면에서 늘 떨어지던 것을 고쳤다(CI 와 같이 커밋된 `openapi.json` 에서 다시 만든 뒤 본다).

## 개발 PC 리허설 — 실제 설치(2026-11-06)

릴리스 `v0.2.0` 번들을 받아 **진짜 `deploy.sh prepare` → `install` → `update` → `remove`** 를 개발 PC(WSL ·

    같고 확인용 DB 의 주인은 앱 계정, 중계 폴더의 상태 · 기준도 원본과 같았다.

    일반 계정은 권한 오류, **sudo 면 그 설치의 기억을 덮는다**. 임시 폴더 아래에 쓴다.

### 진짜 SP 로(2026-11-06)

SP 시험 인스턴스를 하나 더 세워(`jvhubbig` · 8086 · 빈 DB) 같은 원천을 진짜로 미리 보고 · 적용하고 · 대조했다
(`devtools/bench/sp_bench.sh`). 결과는 늘 맞았다(대조 「대상과 같습니다」).

| 원천 행 | 보낸 것 | SP 미리 보기 | SP 적용 | 대조(대상 읽기) |
| --- | --- | --- | --- | --- |
| 2만 | 묶음 하나(4.5MB) | 47초 | 49초 | 10초 |
| 5만 | 묶음 하나(11MB) | 180초 | 194초 | 30초 |
| 10만 | 묶음 하나(22MB) | 653초 | 716초 | 83초 |
| 20만 | 조각 18개(8MB · 선 5,000줄) | 첫 조각 32초 | 「적용」 한 번에 925초(조각마다 미리 보기 · 적용 22–39초) | 273초 |

- **SP 가 선을 넣는 시간은 한 묶음 안의 선 수의 제곱으로 는다.** 객체는 개수에 비례한다(8MB 조각 · 모델 6.4만
  개에 미리 보기 22초). 선 4.2만 줄이 든 조각 하나의 미리 보기가 692초였다 — 위 세 줄도 「객체 1ms + 선 r 천 줄에
  0.4·r² 초」 에 2% 안으로 맞는다. 그래서 조각은 바이트(기본 8MB)와 함께 **선 5,000줄**에서도 끊는다.
- 큰 적용이 끝나면 SP 의 워커가 그래프 지도를 처음 그린다(13.7만 객체에 56초) — 다음 미리 보기는 그 뒤에 줄을 선다.
  틀의 도구는 대기 120초에 「워커가 꺼졌다」 로 멈추므로 relay 는 30분까지 기다린다(`relay_core/sp.py`). 기준정보가
  20만 개를 넘으면 SP 가 지도를 만들지 않는다(`APP-GRAPH-0010` — SP 쪽 한계, 정적 그리기 · 탐색은 된다).
- 20만 행 첫 적재가 **17분**이다 — 묶음 하나로 보냈다면 위 식으로 70분 안팎이고 100MB 상한에 닿는다. 선 상한
  없이 8MB 로만 나눴을 때는 선 4.2만 줄이 한 조각에 몰려 그 조각만 692초였다.
- ~~대조가 대상이 클수록 가파르게 느려진다~~ — 13.7만 객체 83초 → 27.3만 객체 273초(2배에 3.3배). SP 의 목록 API

- 엔진만(가짜 대상) 100만 행까지: 실행 151초 · 본문 226MB · 최대 메모리 4.3GB. 실행이 원천 표를 쓴 뒤 미러를 놓고
  변환하고, 미러를 한 줄씩 흘려 쓰게 해 최대 메모리를 줄였다(20만 행 1.5GB → 0.9GB). 남은 대부분은 틀의 변환기

## 보안 점검(2026-11-06)

AI(MCP) · 토큰이 서버를 시켜 바깥에 닿는 길, 비밀이 새는 길, 파일 · 스크립트를 따로 검토했다. 고친 것:

- **높음 — 토큰으로 계획을 적용할 수 있었다.** 적용 도구는 MCP 에 없지만 `POST /pipelines/<slug>/apply` 를 PAT 로
  바로 부르면 됐다. 이제 판의 사용과 같이 토큰이면 거절한다(`RELAY-0020`). MCP 는 경로에 끼우는 값을 영문 · 숫자 ·
  `-` · `_` 로만 받는다 — `slug="plm-model/apply?"` 가 없는 도구의 경로가 됐다.
- **높음 — 비밀이 엉뚱한 곳 · 엉뚱한 역할로 나갈 수 있었다.** 초안의 대상은 울타리 없이 지도 · 상세가 토큰을 실어
  물었고, 탐색 · 시험은 대상 SP 의 토큰을 원천 인증에 실어 SP 를 부를 수 있었다(XML 원천의 POST — SP 의 적용도
  POST 다). 이제 **사용 중인 정의가 쓰는 비밀은 그 역할 · 그 주소에 묶인다**(`guard.Fence`, `RELAY-0021`), 초안의
  대상에는 묻지 않는다(지도에 「확인하지 않음(초안)」), XML 원천은 GET 과 봉투를 실은 POST 만.
- 중간 — OData 의 다음 쪽 주소가 다른 곳이면 따라가지 않는다(인증 머리글이 그리로 갔다). 값의 출처의 원천 행 ·
  원래 값은 시스템 관리자만(`/sample` 과 같은 선 — 회원은 규칙 · 기준 값만). 어댑터의 숫자 칸에 범위.
- 낮음 — 레시피 판이 서버의 파일(`ontology` · `@파일`)을 가리키지 못한다(`RELAY-0022`). slug 끝의 줄바꿈. 비밀처럼
  보이는 칸 이름(`api_key` · `client_secret` …) · 질의의 키(`?access_token=`)도 거절. 원천의 오류 글에서 그 요청의
  비밀을 지운다(받은 머리글을 되찍는 서버). 토큰이 객체 표현(repr)에 안 찍힌다. 백업 목록은 NUL 로 가르고 기준
  실행의 자리를 확인한다, 복구할 DB 이름 · `APP_NAME` 의 글자를 본다.
- 남긴 것: 레시피 정규식의 지나친 되돌기(ReDoS)와 탐색 · 시험이 화면 요청 안에서 도는 것(작업으로 옮길 일 —
  지금은 숫자 칸의 범위로 줄였다), Apptainer 의 `--no-home` · `--contain`, 포트 없이 적은 주소는 모든 포트가 된다,
  벤더 `sp_pipeline` 의 urllib 이 대상의 리다이렉트를 따른다(벤더는 고치지 않는다). 새 비밀(아직 아무 정의도
  안 쓰는 이름)은 울타리 안 주소로는 실린다 — 그 이름이 플랫폼 밖의 다른 비밀이면 막지 못한다.

## 나눠 보내기 — 30만 행 한계 풀기(2026-11-06)

실제 연동 시스템은 20만 행보다 훨씬 크다. 보낼 묶음이 조각 상한(`target.part_mb`, 기본 8MB)을 넘거나 선이
5,000줄을 넘으면 **조각으로 나눠 차례로 보낸다**(`relay_core/parts.py`). 조각 하나하나가 그대로 SP 의 실행 폴더
(`sends/<때>/parts/001` …)이고, 차례는 객체(참조되는 타입이 먼저) → 선 → 무덤이다. 크기는 진짜 SP 로 잰 것에서
정했다(위 「진짜 SP 로」 — 묶음이 크면 SP 의 선 처리가 제곱으로 늘어, 작게 나누는 편이 전체로 빠르다).

- **조각은 차례로만 미리 본다.** SP 는 적용할 때 미리 본 계획과 지문이 같은지 본다. 앞 조각이 들어가기 전에
  뒤 조각을 미리 보면(가리킬 객체가 아직 없다) 그 계획은 적용되지 않는다. 그래서 실행은 첫 조각만 미리 보고,
  사람이 relay 의 비교(타입마다 생성 · 고침 · 무덤)와 첫 조각의 SP 계획을 읽은 뒤 「적용」 을 한 번 누르면
  조각마다 **미리 보기 → 적용**을 잇는다. 조각이 들어갈 때마다 상태를 적어 두어, 도중에 멈춰도 다음 「적용」 이
  거기서 잇는다.
- **멈춤** — 뒤 조각의 미리 보기에 오류가 나면 거기서 멈추고 그 조각의 계획을 보인다. 앞 조각은 들어가 있다
  (조각마다 전부 아니면 무). 원인을 고친 뒤 「적용」 이 그 조각부터 다시 미리 본다. 대상 SP 화면에서 조각
  하나를 적용해도 relay 가 알아채고 다음 조각으로 넘긴다.
- **접기** — 일부만 들어간 채 원천이 바뀌면, 들어간 조각을 기준에 접어(`runs/<때>-partial`) 거기서 다시
  견준다. 안 그러면 들어간 것을 모른 채 견줘, 그사이 원천에서 지워진 것의 무덤을 빠뜨린다. 대조도 접은
  기준으로 본다.
- 나눠 보내는 계획은 **자동 적용하지 않는다**(첫 적재 · 큰 변경이라 사람이 읽는다). 「사람 적용 N번」 은 계획
  하나를 한 번으로 센다.
- **함께 고친 것** — 무덤만 든 묶음(원천에서 지워진 것만 있는 날)을 틀의 검증이 「묶음이 비어 있습니다」 로
  거절해 실행이 실패했다(SP 는 받는다). relay 의 미리 보기가 그 한 오류만 넘긴다. 또 오류가 난 계획은 같은
  원천으로 다시 실행해도 「같은 계획이 기다립니다」 로 남아, 대상 쪽 원인을 고친 뒤에도 새로 미리 보지
  못했다 — 오류가 난 계획은 다시 실행이 새로 미리 본다.

| 길 | 언제 | 같은 27.3만 객체(20만 행) |
| --- | --- | --- |
| 코어 API(`/api/core/<타입>`) | 견주는 타입이 다 코어로 공개됐을 때 | **36초 · relay 메모리 0.3GB** |
| 묶음 내보내기(`/api/bundles/export`) | 그 밖 — 시스템 관리자 토큰, 타입이 사이드바 묶음 안, **객체 + 선 50만 줄까지** | 31초 · 0.76GB(SP v0.4.74 부터 — 아래) |

- 코어 API 는 (변경 시각, id) 커서로 2,000개씩 — 쪽마다 같은 시간이라 대상이 커도 곧게 는다. 참조가 상대의 **식별자**로
  와서 id 를 풀려고 다른 타입을 쥐고 있을 일이 없다 — 타입마다 흘려 견준다. 코어 줄에는 설명 · 유효 연도가 없어 그
  칸은 「확인 못 함」 으로 센다.
- 시험 인스턴스에서 객체 셋을 직접 바꾸자(칸 값 · 사용 중지 · 삭제) 코어로 읽은 대조가 「다름 1 · 안 씀 1 · 빠짐 1」
  을 정확히 찾았다 — 목록으로 읽은 대조와 같다.
- ~~SP 쪽 결함 — 묶음 내보내기가 큰 묶음에서 실패한다~~ — **SP v0.4.74 에서 고쳤다**(2026-11-06, SP 59eb481). 선을
  고르는 질의가 객체 id 를 출발 · 도착에 한 번씩 매개변수로 넣어 객체 32,768개부터 PostgreSQL 의 한도(65,535)를
  넘었다. 고친 판으로 `sp_bench.sh 200000` 을 다시 돌리자 내보내기로 읽은 대조가 27.3만 객체에 **31초 · relay
  0.76GB** 였다(목록 273초 · 2.3GB, 코어 36초 · 0.3GB). 결과는 같았다(「대상과 같습니다」).
- **대신 상한이 생겼다 — 한 봉투에 객체 + 선 50만 줄**(SP `BUNDLE_EXPORT_MAX_ROWS`). 넘으면 SP 가 읽기 전에 409
  (`APP-BUNDLES-0034`, 큰 타입과 함께)로 거절한다 — 상한을 10만 줄로 낮춘 시험 인스턴스에서 0.7초 만에 거절했고, relay
  는 목록으로 물러나며 보고서에 그 글을 옮겼다. 샘플 PLM 모양이면 원천 20만 행이 34만 줄(객체 27.3만 · 선 6.7만)이라
  **원천 30만 행 남짓부터 내보내기 길은 막힌다** — 그보다 큰 원천은 코어로 공개해야 대조가 빠르다(아래).
- 운영 Datahub 에서 **PLM 정보를 담는 타입을 코어로 공개하는지**가 대조의 속도를 정한다 — **공개하기로
  정했다**(2026-11-06, 아래 ②). 열 타입은 **PLM 파이프라인의 레시피가 쓰는 타입 전부**다 — 운영의 slug 그대로이고
  `plm_` 으로 시작하지 않는 것도 있다. 하나라도 빠지면 대조는 돌되 내보내기 · 목록으로 읽고, 보고서가 빠진 타입을
  말한다(「코어로 열리지 않은 타입(…)」). 공개하지 않으면 목록으로 읽는데, 시간은 대상 크기의 제곱으로 · 메모리는
  크기에 비례해 는다(27.3만 객체에 2.3GB).
  `plm-core.json` 의 「코어」는 「모든 설치가 함께 쓰는 정의」라는 뜻이고 `"core": true` 가 없다 — 넣어도 공개되지
  않는다. 허브 → 쌍둥이(`hub_pull`)도 묶음 내보내기라 공개가 필요 없다. relay 의 묶음에는 `core` 칸이 없고 SP 의 정의
  가져오기는 보낸 칸만 바꾸므로(`ontology/importer._assign`), relay 가 적용해도 공개가 꺼지지 않는다.

## 실행의 메모리 묶기 — 나눠 변환 · 나눠 비교 · 흘려 쓰는 미러(2026-11-06)

실행은 원천 전체를 매번 메모리에 들었다 — 50만 행에 변환 2.2GB · 비교 1.7GB · 미러 1.1GB(단계마다의 최대). 실제
원천은 20만 행보다 훨씬 크므로, **원천이 커져도 실행의 메모리가 늘지 않게** 묶었다. 하는 일(미러 전체를 다시
변환하고 기준과 견준다)과 결과는 그대로다.

- **변환**(`relay_core/table.py`) — 원천 표를 파일에서 흘려 읽는다. 행이 바구니 하나(`spill.BUCKET_ROWS`, 10만 행)를
  넘으면 타입마다 **식별자의 해시로**, 관계마다 **출발점의 해시로** 행을 바구니에 나눈다(그 타입이 읽는 칸만). 같은
  식별자의 행은 한 바구니에 원래 차례로 드니, 틀의 모으기(`gather` · `gather_edges`)를 바구니마다 불러도 객체 · 선 ·
  갈린 값이 같다. 결과는 첫 행 차례로 다시 이어 틀과 같은 이름 · 크기의 파일로 쓴다. 틀(`vendor`)은 고치지 않았다 —
  틀의 함수를 바구니마다 부른다. 행을 그냥 잘라 변환하면 **틀린다** — 과제처럼 여러 행이 한 객체로 모이는 타입은
  같은 식별자의 행이 다 한 조각에 있어야 한다.
- **같다는 것은 시험이 묶는다**(`tests/unit/test_relay_table.py`) — 틀의 변환기와 실행 폴더를 바이트로 견준다:
  해석기와 그 검증, 참조 대조(미해결 · 그대로 · 비움), 모으는 칸(collect · join), 갈린 값, 빈 식별자 · 빈 행, 선의
  속성 · 근거, cp949, 5,000줄이 넘는 타입. 미해결의 차례도 틀과 같게 다시 세운다. 보고서는 수가 같고 **횟수가 같은
  예시끼리의 차례만** 다를 수 있다(시험의 표에서는 같았다). 틀을 새로 가져오면(`sync_sp_pipeline.sh`) 이 시험이 먼저
  본다.
- **비교**(`diff.delta`) — 기준과 이번 출력을 정체(타입 · 식별자 · 선의 세 끝)의 해시로 바구니에 나눠 견주고, 보낼
  줄은 이번 출력의 차례로 다시 잇는다. 바구니 하나(= 한꺼번에)와 여럿이 파일까지 같다.
- **미러**(`Workdir.merge_mirror`) — 파일의 키 차례 행과 받은 것을 이어 새 파일을 쓴다. 메모리에는 받은 것만 든다
  (증분이면 몇 건). 반영의 셈은 `Mirror.apply` 와 같다(무작위 시험). 옛 판(0.2.2 까지)의 들여쓴 미러도 읽는다. 원천
  표본 화면 · 레시피 시험도 미러를 흘려 읽는다.
- 바구니는 `work/<때>.spill` · `work/<때>.send.spill` 에 두고 끝나면 지운다(도중에 죽으면 정리가 지운다). 같은
  프로세스가 쓰고 곧 읽는 임시 파일이라 pickle 로 1,000줄씩 묶는다 — 줄마다 JSON 이면 비교가 두 배 넘게 걸렸다.

엔진만(가짜 대상, `relay_bench.py` — 단계마다 그 단계의 최대 메모리):

| 원천 행 | 첫 적재(실행) | 1% 증분(실행) | 전(첫 적재 = 증분) |
| --- | --- | --- | --- |
| 20만 | 35초 · 0.54GB(받은 행 0.28GB) | 36초 · **0.38GB** | 30초 · 0.9GB |
| 50만 | 89초 · 1.29GB(받은 행 0.63GB) | 77초 · **0.38GB** | 75초 · 2.2GB |
| 100만 | 188초 · 2.56GB(받은 행 1.22GB) | 159초 · **0.38GB** | 151초 · 4.3GB |

증분은 첫 적재와 다른 프로세스에서 쟀다 — 같은 프로세스면 첫 적재가 남긴 메모리(파이썬이 돌려주지 않는다) 위에서
재게 된다. 첫 적재의 최대에는 어댑터가 넘긴 행 목록(「받은 행」)과 보낼 본문 몫(조각 나누기, 아래)이 든다. 바구니는
디스크를 잠깐 쓴다 — 50만 행에 변환 116MB(원천 표의 2배) · 비교 163MB, 끝나면 지운다.

- **대가는 시간이다** — 바구니에 쓰고 다시 읽는 몫. 100만 행에 첫 적재 151초 → 188초, 증분 151초 → 159초. 변환만
  보면 틀의 변환기보다 13%(50만 행 46초 → 52초), 비교는 두 배(10초 → 21초)다.
- **남은 것 — 아직 원천 크기에 비례한다:** 첫 적재 · 전량을 받는 날 어댑터가 넘기는 행 목록(원천 행당 약 1.2KB —
  어댑터가 목록으로 낸다), 보낼 것이 클 때의 조각 나누기(전체 본문의 지문을 만들려고 본문을 한 번 든다 — 첫 적재 ·
  레시피를 바꿔 다 바뀐 날, 행당 약 1.3KB), 대조(기준 출력을 통째로 든다 — 7일마다, 20만 행에 0.3GB), 값의 출처가
  원천 표 없이 미러로 찾을 때. 다음에 줄일 차례는 어댑터(받은 행을 파일로)와 조각 나누기(지문을 흘려 만들기)다.

## 운영 Datahub 에 처음 붙는 순서

운영 서버는 이 PC 에서 닿지 않는다 — 아래는 그 자리에서 하는 순서다. 개발 PC 에서는
`devtools/sandbox_sp` 가 같은 순서를 돈다.

1. **첫 미리보기(덮지 않음)** — `relay run`(기본 `human_edits: keep`). 계획의 줄이 셋을 알려 준다:
   PLM 과 값이 다른 객체(「고침」), Datahub 에만 있는 것은 안 건드림, 그리고 **사람이 화면에서 고친
   칸** — SP 는 사람이 고친 칸을 칸마다 기록해 두고, 기본으로는 덮지 않고 그 줄에 「안 덮음」 으로
   적는다. 고친 값이 있는지 모른다는 물음의 답이 여기서 나온다. **이 계획은 적용하지 않는다.**
2. **정한다** — 사람이 고친 칸을 PLM 값으로 덮을지. PLM 이 정본이니 덮는 것이 기본이다. 남겨야 할 것이
   있으면 그것은 PLM 에서 먼저 고친다.
3. **잠그고 연다** — PLM 정보를 담는 타입(운영의 slug 그대로 — `plm_` 으로 시작하지 않는 것도 있다)의 정의를
   `source: plm` 묶음으로 넣는다(한 번 · 시스템 관리자 · `ontology:write`). 그 뒤로는 Datahub 화면 · API 에서
   사람이 못 고친다(409 「plm 가 관리하는 타입」). 잠근 뒤에도 relay 의 묶음은 같은 `source` 라 통과한다. 같은
   정의의 타입마다 `"core": true` 를 적어 **코어로도 연다**(2026-11-06 결정 — 대조가 코어 API 로 읽는다).
4. **덮어 넣는다** — `relay run --human-edits overwrite` 로 다시 미리 보고, 계획을 읽고 `relay apply`.
   사람이 고쳤다는 표시도 함께 지워진다.
5. 그 뒤로는 기본(`keep`)으로 돈다 — 잠겨 있어 새로 생길 사람의 수정이 없다.
6. **대조로 확인한다** — 화면 「대조」(또는 `relay reconcile`)가 「대상과 같습니다」 여야 한다. 어긋나면
   다름의 칸을 먼저 읽는다 — 레시피의 값 모양이 대상과 다른 것이면 레시피를 고치고, 진짜 어긋남이면 보정
   계획으로 맞춘다. 「대상 읽기」 가 「코어 API」 인지도 본다 — 아니면 「결과」 가 코어로 안 연 타입을 말한다.
   그 뒤로는 타이머가 7일마다 본다.

잠금은 PLM 만의 것이 아니다 — SP 의 **타입마다** 관리 주인을 하나 둔다. MES 로 채우는 제조 데이터허브의
타입은 `mes`, 허브가 다른 SP 로 뿌린 사본은 받는 쪽에서 `hub` 로 잠긴다. 사람이 SP 에서 직접 만들고
고치는 타입(그룹 전용 기록 등)은 잠그지 않는다. 주인이 하나라 **한 타입은 한 길로만** 채운다(ADR 0001).
