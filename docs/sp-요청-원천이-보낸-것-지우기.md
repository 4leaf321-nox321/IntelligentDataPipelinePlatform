# SP 요청 — 원천이 보낸 것을 원천이 지우게 (2026-11-23)

datarelay 가 SP 에 넣은 객체는 **지울 길이 없다.** 시험으로 보낸 것도, 잘못 보낸 것도 그렇다. datarelay
쪽은 「보낸 것 걷어내기」를 만들었지만(아래), SP 가 받는 쪽에서 **사용 중지까지만** 하므로 객체가
목록에 남는다. SP 에 두 가지를 요청한다.

## 지금 SP 에서 막히는 곳

| 하려는 일 | 막는 곳 | 까닭 |
| --- | --- | --- |
| 잠긴 타입의 객체를 화면에서 지우기 | `objects/routes.py` `delete_object` → `managed.require_objects_editable` (OBJECTS-87) | 정본은 원천 — 고치면 다음 받기가 덮는다 |
| 원천이 무덤으로 지우기 | `bundles/tombstones.py` — 객체 무덤은 `status = "deprecated"` | 「받는 쪽은 지우지 않는다」(가리키는 관계 · 첨부 보호) |
| 잠긴 타입을 지우기 | `ontology/routes.py` `_type_deletion` → `managed.require_definition_editable` | 정의도 원천의 것 |
| 다 사용 중지된 타입을 지우기 | 같은 곳 — `deleted_at IS NULL` 을 「살아 있는 객체」로 센다 | 사용 중지는 지운 것이 아니다 |

네 줄이 각각은 맞지만 겹치면 시험 데이터를 영영 못 치운다.

## datarelay 가 이미 한 것 (v0.2.14 예정)

- 파이프라인 상세 「보낸 것 걷어내기」, MCP `pipeline_retract`
  - 걷어낼 범위는 셋 중 하나로 고른다: 이 파이프라인이 넣은 것 전부, 타입 전부, 식별자 몇 개.
  - datarelay 는 그 객체와 닿는 선을 무덤(`tombstones`)으로만 든 source 묶음을 `apply: false` 로
    올린다. 사람이 SP 「작업」 화면에서 적용한다. 묶음에는 원천 기록(origin, ADR 0087)이 함께 실린다.
  - 그 파이프라인이 넣지 않은 것(기준에 없는 식별자)은 datarelay 가 보내기 전에 거절한다.
  - 걷어낸 것은 datarelay 의 기준에서도 빠진다. 그래서 대조가 되살리지 않는다.
- 지금 SP 는 이 무덤을 **사용 중지**로 받는다. datarelay 화면 · 결과문에도 그렇게 적어 두었다.

## 요청 1 — 객체 무덤에 「지우기」

객체 무덤 한 줄(`ObjectTombstoneIn`)에 선택 칸을 더한다.

```json
{"tombstones": {"objects": [
  {"type_slug": "plm_model", "key": "M-TEST-01", "merged_into": null, "action": "delete"}
]}}
```

- `action`: `"deprecate"`(기본값 — 지금과 같음) · `"delete"`.
- `delete` 는 화면의 삭제와 같은 일이다. `deleted_at` 을 채우고 이력과 감사 기록은 남긴다. 가리키는
  것이 있으면 화면의 `mode=block` 처럼 막고, 무엇이 걸렸는지 계획의 그 줄 오류로 보인다.
- **그 타입을 잠근 원천의 묶음만** 쓸 수 있다(`type.managed_by == source`). 아니면 그 줄을 오류로 둔다.
  사람이 만든 타입 · 남의 원천 타입은 지금처럼 화면의 일이다.
- **이미 사용 중지된 객체에도** 된다. 요청 1이 나오기 전에 걷어낸(사용 중지된) 시험 데이터를 나중에
  지울 수 있어야 한다.
- 계획에서는 「삭제」 와 「사용 중지」 를 다른 이름 · 다른 건수로 보인다. 적용하는 사람이 무엇이
  사라지는지 읽어야 한다.
- 옛 SP 는 모르는 칸을 무시한다(지금 `ObjectTombstoneIn` 에 `extra` 설정이 없다). 그러면 지금처럼
  사용 중지가 된다. datarelay 는 대상의 `/api/health` 판으로 지원 여부를 보고, 안 되는 SP 에는 「사용
  중지만 됩니다」 라고 말하겠다.

## 요청 2 — 원천 타입의 잠금 풀기

시험용 타입(`plm_demo_lot` 같은)은 객체를 다 지워도 타입이 남는다. 잠긴 타입은 정의를 못 지우기
때문이다. 다음 중 하나를 요청한다(SP 가 고른다).

- **가) 화면의 「잠금 풀기」**(시스템 관리자, 감사 기록, 확인 창). `managed_by` 를 비운다. 그 뒤로는
  사람이 객체 · 타입을 평소처럼 지운다. 원천이 같은 타입을 다시 보내면 다시 잠긴다(지금 규칙
  그대로). 경고 문구에 「원천이 아직 보내는 중이면 다음 받기가 다시 잠그고 덮어씁니다」 를 적는다.
- **나) 원천 묶음으로 타입 지우기**(`ontology` 에 지울 타입 목록). 그 원천이 잠근 타입이고 살아 있는
  객체가 없을 때만 된다. 지운 객체가 남아 있으면 ADR 0008 의 영구 삭제 확인을 계획에 싣는다.

datarelay 는 **가)** 를 권한다. 파이프라인을 그만둘 때(원천을 끊을 때)도 같은 일이 필요하고, 타입을
지우는 것은 사람이 SP 에서 정하는 편이 맞다.

## SP 에서 받고 싶은 답

1. 요청 1의 칸 이름 · 값(`action: "delete"` 그대로면 좋다)과 나오는 SP 판.
2. 요청 2를 가) · 나) 중 무엇으로 할지, 나오는 판.
3. `delete` 가 가리키는 것이 있는 객체를 막을지, 화면의 `detach`(참조 비우고 관계 끊기)를 고를 수
   있게 할지. datarelay 는 「막고 줄 오류로 보이기」 만으로 충분하다.

## datarelay 쪽에서 이어서 할 일 (SP 답을 받은 뒤 — 2026-11-24 에 했다)

- 걷어내기 무덤에 `action: "delete"` 를 싣는다. 화면에서 「사용 중지 / 지우기」 를 고르게 하고, 대상
  SP 판이 낮으면 사용 중지만 하게 한다.
- 요청 1 이전에 걷어낸 것도 「지우기」 로 다시 보낸다. 대조는 이미 대상의 객체를 사용 중지된 것까지
  읽는다. 그래서 이 원천이 잠근 타입에서 「사용 중지이고 기준에 없는 것」 을 찾아 고르게 한다.
- 선 무덤에 `dst_type` 을 싣는다. datarelay 는 관계 종류의 도착 타입을 이미 안다.

## SP 의 답 (2026-11-24)

1. 칸은 `action: "delete"` 그대로다. SP 0.4.101 에서 나온다. 0.4.100 까지는 이 칸을 무시하고 사용 중지한다.
2. 잠금은 가) 화면의 「잠금 해제」 로 한다.
3. `delete` 는 막기만 한다(`detach` 없음). 선 무덤의 `dst_type` 은 SP 가 이미 받는다.
