# 외부 시스템 ↔ Standard Platform 연동 지침서

**읽는 사람:** 상대 시스템(MatNexus · TestScope · ReportArchive · Standard Platform 쌍둥이)을
만드는 개발자. 이 문서 하나만 보고 양방향 연동을 만들 수 있게 적었다 — Standard Platform(이하
**SP**)의 코드를 보지 않아도 된다.

**확정판 — 0.4.15 판 (2026-09-24).** 규약은 §7 과 §12-A 에서 **확정했다** — 여기 적힌
호출·필드·규칙은 그대로 구현되어 있고, ReportArchive 와의 실연동에서 처음부터 끝까지 돌려
보았다(§13). 시스템마다 달라지는 것(대상 타입 · 시각 · 담당자 · 코드값)은 §12-B 의 양식에
채워 양쪽이 같은 사본을 갖는다. **§12-B 를 안 채운 연동은 켜지 않는다** — 빈칸은 나중에
사람이 기억으로 메우게 되고, 양쪽의 기억은 다르다.

**보강 (2026-10-06).** 받는 쪽 규칙 6 ~ 11(§4.2 — 같은 행 두 번 · 재적재의 부재 대조 · 되살림 ·
합쳐진 쪽의 선 · 참조 칸의 옛 식별자 · 두 가지 404), 웹훅의 실제 이벤트 이름과 본문(§4.5), 정의 판
(`revision`)이 허브를 다시 띄워도 같은 값(0.4.40 까지는 재시작마다 바뀌었다).

**보강 (2026-10-21).** 연동 키트를 **받는 쪽 AI 가 읽고 만드는 패키지**로 바꿨다(§4.2) — AI 용 구현
지시서 · 정답 구현 · 시험장(가짜 SP 와 채점기) · 예전 키트를 받은 쪽의 안내(`UPGRADE.md`). 정답 구현은
규칙 1 ~ 11 을 모두 지킨다(키트 판 `2026-10-21` — 그 전 판은 식별자 바뀜 · 부재 대조 · 지운 객체의 선 ·
두 가지 404 를 놓쳤다). 선 창구는 **양 끝이 살아 있는 선만** 보낸다(그 전에는 도착이 지워진 선도
보냈다 — 처음 받는 쪽이 받은 적 없는 `key` 를 끝으로 쥐었다).

**보강 (2026-10-22).** SP 의 조회가 기본으로 **부서와 상관없이 전원**에게 열렸다(ADR 0034) — 토큰 주인의 소속이
받는 범위를 줄이지 않는다. 그래서 기본 설치에서는 `hidden` 무덤(지킬 것 4)이 생기지 않는다. 계약은 그대로다 — 설치가
`VIEW_SCOPE=department` 로 좁히면 다시 생긴다(좁히는 날 받던 것이 표식 없이 빠지므로 처음부터 다시 받는다).

**보강 (2026-11-03).** 연동 키트 `2026-11-03` 판 — 지시서가 **받은 선을 받는 쪽 플랫폼에 넣는 법**(반영 층의 선:
도착은 `dst_type` 의 표에서, 연결은 레코드를 가리키게, SP 에서 온 연결만 끊기)과 관계의 뜻(유효 기간 · 수량 ·
계보, ADR 0039 ~ 0041 — §4.2)을 쓰는 법, 이 창구로 오지 않는 것을 적는다. 시험장의 층 2 확인표에
선 표가 붙었다. 받기 규칙과 정답 구현의 동작은 `2026-10-21` 판과 같다.

## 0. 30초 요약

| 방향 | 무엇을 | 누가 만드나 |
| --- | --- | --- |
| 그쪽 → SP | SP 가 **주기적으로 읽어 간다** | 그쪽이 읽기 API 하나(§3) |
| SP → 그쪽 | 그쪽이 **주기적으로 읽어 간다** — 코어 API(§4.2) | SP 는 이미 있다. 그쪽은 받는 코드만 |
| SP → 그쪽 (즉시) | 바뀐 순간 알림 | 그쪽이 수신구 하나(§4.4). 선택 |
| 그쪽 → SP (밀어넣기) | 그쪽이 SP 에 직접 넣는다 | SP 는 이미 있다. 선택(§5) |

**받는 쪽은 AI 코딩 도우미로 만들 수 있다.** SP 의 코어 화면에서 내려받는 **연동 패키지**(§4.2)에
AI 용 구현 지시서 · 정답 구현 · 시험장(가짜 SP)이 들어 있다. 받아 오기만이면 정답 구현을 그대로
돌려도 되지만, **받은 것을 자기 플랫폼의 표 · 화면에 넣는 반영은 받는 쪽이 만들어야 한다** — 그
플랫폼의 구조를 SP 가 모르기 때문이다.

**형식은 하나다.** SP 가 쓰는 묶음 형식(`sp-bundle/1`, §6) 을 양쪽이 그대로 쓴다. 시스템마다
형식을 만들고 어댑터로 잇기 시작하면, 어댑터는 n² 로 늘고 **둘 중 하나만 고쳐진 날** 조용히
틀린 데이터가 흐른다.

## 1. 말 맞추기

| 말 | 뜻 | 예 |
| --- | --- | --- |
| **타입**(type) | 표 하나. `slug` 로 부른다 | `supplier`, `material` |
| **속성**(property) | 타입의 칸. `key` 로 부른다 | `grade`, `melting_point` |
| **관계 종류**(relation type) | 객체 사이의 선. `slug` 로 부른다 | `supplied_by` |
| **객체**(object) | 타입의 한 행 | 「ACME」 공급사 |
| **식별자**(key) | 객체를 가리키는 **안 바뀌는 문자열** | `ACME-001` |
| **별칭**(alias) | 같은 것을 부르는 다른 이름 | 「앤시스」 ↔ 「Ansys」 |
| **묶음**(bundle) | 정의 + 객체 + 관계를 담은 JSON 하나 | §6 |
| **작업**(job) | 오래 걸리는 일. 넣고(202) 나중에 결과를 받는다 | §4.2 |

## 2. 원칙 다섯

1. **형식은 하나** — `sp-bundle/1`. 그쪽 내부 모델이 달라도 **경계에서만** 이 모양으로 낸다.
2. **식별자는 그쪽이 정하고, 절대 바꾸지 않는다.** 바뀌는 순간 SP 는 그것을 「새것」 으로 보고
   하나를 둘로 만든다. 자동 증가 정수여도 좋고 UUID 여도 좋다 — **안 바뀌기만 하면 된다.**
3. **지우지 말고 사용 중지로 보낸다**(`status: "deprecated"`). 받는 쪽에는 그것을 가리키는
   참조가 이미 있고, 행이 사라지면 그 참조는 빈 칸이 된다.
4. **시각은 ISO-8601 UTC** — `2026-09-22T01:23:45Z`. 로컬 시각·오프셋 없는 문자열은 받지 않는다.
5. **미리 보기 → 적용.** 넣는 길에는 언제나 「무엇이 바뀌는지 먼저 보는」 단계가 있다. 자동
   연동이라도 처음 몇 번은 사람이 그 표를 본 뒤 켠다.

## 3. 그쪽이 만들 것 ① — SP 가 읽어 갈 API

SP 에는 **데이터 소스**라는 장치가 있다. 주기마다 바깥 JSON 을 읽어 우리 타입의 행으로 바꾸고,
칸 대응·값 대응·다시 찾기·미리 보기까지 SP 가 한다. **그쪽이 만들 것은 읽기 엔드포인트 하나뿐이다.**

### 3.1 모양

```
GET  {base_url}/{path}?page=1&page_size=500
Authorization: Bearer {토큰}
Accept: application/json
```

응답:

```json
{
  "items": [
    {
      "id": "ACME-001",
      "name": "ACME 정밀",
      "country": "KR",
      "grade_code": "A",
      "is_active": true,
      "updated_at": "2026-09-22T01:23:45Z"
    }
  ],
  "total": 1234,
  "page": 1,
  "page_size": 500
}
```

### 3.2 규칙

| 규칙 | 왜 |
| --- | --- |
| 항목은 **평평한 객체**(중첩 금지, 값은 문자열·숫자·불리언·null) | 중첩을 펴는 규칙을 양쪽이 따로 만들면 갈린다. 중첩이 꼭 필요하면 그쪽에서 `owner_name` 처럼 펴서 낸다 |
| 항목마다 **안 바뀌는 식별자**를 한 칸에 | §2-2 |
| 항목마다 `updated_at` (ISO-8601 UTC) | 언제 것인지 모르면 되돌릴 수도, 늦은 것을 버릴 수도 없다 |
| 지운 것은 **행을 빼지 말고** `is_active: false` 또는 `deleted: true` 로 | §2-3 |
| 열 이름은 안 바꾼다. 늘리는 것은 자유 | SP 의 칸 대응이 열 이름에 물려 있다 |
| 같은 요청은 같은 답 (정렬 고정) | 쪽 넘김 중에 순서가 바뀌면 행이 빠지거나 겹친다 |
| 목록은 **전량**을 낼 수 있어야 한다 | 첫 연동과 정합성 점검은 전량 대조로 한다 |

### 3.3 쪽 넘김 — 셋 중 하나만 고르면 된다

| 방식 | 요청 | 끝나는 조건 |
| --- | --- | --- |
| `page` | `?page=1&page_size=500` | 받은 행이 `page_size` 보다 적으면 끝 |
| `offset` | `?offset=0&limit=500` | 같음 |
| `cursor` | `?cursor=xxx&page_size=500` | 응답의 `next` 가 비면 끝 |

SP 는 셋 다 읽는다. 파라미터 이름이 다르면(예: `perPage`) **그쪽 이름을 알려 주기만 하면 된다** —
SP 쪽 설정에 적는다. 고칠 코드는 없다.

### 3.4 인증

넷 중 하나. **SP 는 비밀을 화면에 다시 보여 주지 않는다.**

| 방식 | 보내는 것 |
| --- | --- |
| `bearer` | `Authorization: Bearer {토큰}` |
| `basic` | `Authorization: Basic {base64}` |
| `header` | 임의 헤더 — 예 `X-API-Key: {값}` |
| `none` | 폐쇄망 안에서만 |

토큰은 **읽기 전용**으로 발급해 준다. 연동이 쓰기를 할 일은 이 방향에 없다.

### 3.5 OData · 파일도 된다

그쪽이 이미 OData v2/v4 를 내고 있으면 그대로 붙는다(엔티티 셋·`$filter`·`$select`·쪽 넘김을
SP 가 안다). CSV · Excel · JSON 파일을 공유 폴더나 URL 로 떨구는 방식도 된다. **새로 만들 때만**
§3.1 을 쓰면 된다.

### 3.6 SP 쪽에서 하는 일 (참고)

그쪽이 보낸 열을 SP 의 칸에 잇는 것은 SP 화면에서 한다:

```
id          → key
name        → label
grade_code  → properties.grade   값 대응: {"A": "1등급", "B": "2등급"}
country     → properties.country
```

표에 없는 코드가 오면 **그 행은 오류**로 세워 둔다(조용히 통과시키면 고를 값이 오염된다). 그래서
**코드 목록이 늘면 미리 알려 줘야 한다** — §12-B ③.

## 4. 그쪽이 만들 것 ② — SP 에서 받아 가기

SP 는 **이미 다 있다.** 그쪽은 받는 코드만 쓰면 된다. 셋 중 필요한 것만 고른다.

### 4.1 토큰 받기

SP 관리자가 그쪽에 **개인 접근 토큰(PAT)** 을 발급한다. 모든 요청에 붙인다:

```
Authorization: Bearer standardplatform_pat_xxxxxxxxxxxx
```

범위(scope)는 넷과, 이 설치가 켠 **확장마다 하나**다. **코어만 받아 갈 것이면 `core:read` 하나를 청한다** — 그러면 그 토큰은
코어 밖을 못 읽는다. 연동 하나 때문에 사내 전체가 열리지 않게 하는 자리다.

| 범위 | 할 수 있는 일 |
| --- | --- |
| `core:read` | **코어로 연 타입만**(`/api/core`) — 바깥 시스템은 대개 이것 하나 |
| `read` | 그 계정이 볼 수 있는 읽기 전부 + 내보내기 |
| `objects:write` | 객체·관계 넣기·고치기, 첨부 붙이기·떼기 |
| `ontology:write` | 정의(타입·속성·관계 종류) 바꾸기 |
| `<확장>:write` | 그 확장의 자료 바꾸기(예 `caegroup:write` — 디지털 트윈 역량). **읽기는 `read` 로 된다.** 확장을 켠 설치에서만 고를 수 있다 |

토큰은 **시스템마다 따로** 받는다 — 누가 무엇을 읽었는지 감사에 남고, 한 곳만 끊을 수 있다.

발급은 SP 시스템 관리자가 한다. 발급된 토큰이 코어를 읽을 수 있는지는 SP 화면
**온톨로지 › 코어 › 「액세스 토큰」** 탭에서 확인한다 — 범위가 `core:read` 인 것은 「코어 전용」,
`read` 인 것은 「전체 읽기」 로 표시된다. 만료일도 같은 표에 있다.

### 4.2 길 ① 코어 API — **주기 동기화는 이 길이다**

SP 가 **코어로 공개한 타입**만 나가는 창구다. 세 가지가 목록 API 와 다르다: 공개한 것만
나가고, **지난번 이후**만 주고, **사라진 것도 알려 준다.**

#### 코드를 쓰기 전에 — 연동 패키지

공개 측 화면 **온톨로지 › 코어 › 「연동 키트 다운로드 (zip)」** 에서 한 벌이 나온다
(`sp-core-client.zip`). 이 설치의 연동 주소와 공개 타입이 **이미 채워진 채로** 만들어진다. 받는 쪽은
대개 이 폴더를 **자기 AI 코딩 도우미에게** 주고 `00-START-HERE.md` 의 문장을 붙여 넣는다.

| 파일 | 누가 | 하는 일 |
| --- | --- | --- |
| `00-START-HERE.md` | 사람 | 이 설치의 주소 · 공개 타입 · 정의 판, AI 에게 붙여 넣을 문장, 완료 확인표 |
| `01-AI-GUIDE.md` | AI | 구현 지시서 — 두 층 구조(받기 · 반영), 사본 표, 받는 쪽 규칙 16가지, 객체와 선의 반영(수량 · 계보 · 유효 기간), 이 창구로 오지 않는 것, 사람에게 물을 것, 완료 조건 |
| `sp_core_pull.py` · `README.md` | AI · 사람 | **정답 구현**(파이썬 한 파일, 의존성 `requests`)과 사용법. 받기 층으로 그대로 써도 된다 |
| `testbed/` | AI | **시험장** — 가짜 SP(표준 라이브러리만)가 8단계로 식별자 변경 · 합치기 · reset · 커서 오류 · 정의 판 변경 · 공개 거둠 · 범위 줄어듦을 일으키고, 채점기가 받은 결과를 정답과 비교한다 |
| `check.sh` · `config.example.ini` | 사람 | 실제 SP 연결 점검 · 정답 구현 설정 |
| `UPGRADE.md` · `CHANGES.md` | 사람 | 예전 키트를 받은 쪽이 할 일 · 판마다 바뀐 것 |

정답 구현만 돌리면 `out/` 에 **CSV(수신 이력)** 와 **SQLite(현재 상태)** 가 남는다 — SP 와 맞춰 둔
사본이다. 끝나는 값은 `0` 정상 · `1` 멈춤 · `2` 사람이 볼 것 있음(공개 안 된 타입 · 절반 넘게 안 와서
정리를 멈춤)이라 야간 작업의 경보로 쓴다. 아래 반복문과 「지킬 것」 은 정답 구현이 하는 일과 같다.
시험장은 실제 창구와 응답의 칸 이름이 같은지 SP 쪽 시험이 지킨다.


**타입 이름과 칸 이름을 코드에 박지 말고 여기서 읽는다.** `revision` 은 공개된 정의의 판이다 —
받는 쪽 해석이 달라지는 변경(칸 · 자료형 · 여러 값 여부 · 참조 대상 · 고를 값 · 열린 관계 종류)이면
값이 바뀌므로 「구조가 달라졌네」 를 코드로 알아챌 수 있다. 이름 · 설명 같은 표시 문구로는 안
바뀐다. 그래도 통지 전에 **직전 카탈로그와 칸 목록을 대조**해 두면, 판 계산 방식이 바뀌는 날(한 번
바뀐다) 헛통지가 안 나간다.

`/api/core` 와 `/api/core/` 는 **둘 다 같은 응답이다.** 끝 슬래시를 붙여 부르고 307 을 따라가지
않는 클라이언트가 실제로 있었다(§13) — 그래서 별칭을 두었다.

**조회는 공개 측 기록에 남는다**(`core.pull` — 어느 타입 · 몇 행 · 어느 시각 이후 · 어느 토큰).
SP 화면 **코어 › 「최근 조회 이력」** 탭에서 양쪽이 같은 사실을 본다. 「어제 받았는데 값이 없다」
를 맞대 볼 자리가 여기다. 받아 갈 것이 없던 조회는 남기지 않는다.

**응답은 두 층이다.** 봉투(`as_of` · `next` · `items`, 그리고 행의 `key` · `label` · `status` ·
`updated_at` · `deleted` · `merged_into`)는 **어느 타입이든 같다.** 알맹이(`properties`)는 그
타입이 정한 칸이라 설치마다 다르고, 무엇이 있는지는 카탈로그가 말한다. 그래서 속성을 행에
펼치지 않는다 — 펼치면 누가 속성 키를 `label` 이나 `deleted` 로 만드는 날 봉투와 부딪힌다.

#### 받는 쪽의 반복문

```
since = 내DB.읽기("sp_material_as_of")      # 처음엔 없음 → 전량
cursor = null
while True:
    res = GET /api/core/material?since={since}&cursor={cursor}
    for row in res["items"]:
        if row["deleted"]: 내DB.비활성(row["key"], 합쳐진곳=row.get("merged_into"))
        else:              내DB.upsert(key=row["key"], ...)
    cursor = res["next"]
    if not cursor: break
내DB.저장("sp_material_as_of", res["as_of"])   # 끝까지 받은 뒤에만
```

지킬 것:

1. **`as_of` 를 그대로 되돌려 준다.** 그쪽 시계로 시각을 만들면 몇 초 차이로 그 사이 행이 새고,
   샌 줄은 아무도 모른다. 우리가 주는 `as_of` 는 **지금 도는 적재보다 앞서지 않는다** — 긴
   적재(백필)가 도는 중에 받아 가면 같은 지점을 한 번 더 물을 뿐, 잃지는 않는다. **그래서
   백필 동안 받기를 멈출 필요가 없다** — 끝나면 그때부터 전부 따라온다. 얼마나 뒤처져
   있는지는 공개 측 **코어 현황**의 `watermark_lag_seconds` 가 말한다(줄지 않고 계속 커지면
   공개 측에 열어 두고 잊은 세션이 있다는 뜻이니 공개 측에 알린다).
2. **`next` 가 있으면 `as_of` 는 `null` 이다.** 쪽이 남았는데 시계를 옮기면 남은 쪽을 영영 안
   받는다 — **끝까지 받은 뒤에만** 저장한다.
3. **`key` 를 그쪽 DB 에 저장한다.** 그래야 다음 동기화가 「고침」 이 되지 「새로 만들기」 가 안 된다.
4. **`deleted` 를 처리한다.** 지우지 말고 비활성으로 두는 편이 안전하다. `merged_into` 가 있으면
   그쪽 참조를 그 `key` 로 옮긴다. **`renamed_from` 이 있으면** 그 옛 식별자로 제가 가진 행을
   찾아 키를 옮긴다 — 안 그러면 같은 것이 둘이 된다. **`hidden: true` 도 함께 오면** 지운 것이
   아니라 그 토큰으로 더 이상 안 보이게 된 것이다(소유 부서가 토큰 주인이 못 보는 부서로 옮겨 감 —
   **부서 통폐합으로 옮긴 것도 온다**, 2026-10-08). 이름 · 칸은 안 오므로 가진 값은 두고 비활성만 한다.
5. **모르는 칸은 무시한다.** 우리가 칸을 늘려도 그쪽이 안 깨지는 이유가 이것이다.
6. **같은 행이 두 번 올 수 있다.** 경계 시각과 긴 적재 구간에서 그렇다 — 덮어쓰면 해가 없다.
7. **`since` 없이 받으면 지워진 것은 안 온다.** 처음 받을 때는 그게 맞지만, 이미 받아 둔 것이 있는
   상태에서 처음부터 다시 받으면(재적재) 「지워졌다」 를 들을 길이 없다. **끝까지 받은 뒤 이번에 안 온
   것을 비활성으로 둔다**(부재 대조) — 쪽이 여러 번(여러 실행)에 걸치면 **마지막 쪽까지 받은 뒤에만**
   대조한다. 중간에 실패한 채로 대조하면 아직 안 받은 것이 지워진다. 객체가 다른 부서로 옮겨 가
   안 보이게 된 것은 `hidden` 무덤으로 오지만(4), **토큰 주인의 소속이 줄어** 못 보게 된 것은 표식
   없이 빠지므로, 주 1회쯤 전량을 받아 대조해 두면 안전하다.
8. **지워졌던 것이 되살아날 수 있다.** 같은 `key` 가 `deleted: false` 로 다시 오면 다시 살린다.
9. **합쳐진 쪽의 선은 「끊긴 선」 으로 오지 않는다.** 합치기는 진 쪽의 선을 이긴 쪽으로 **옮기므로**
   이긴 쪽 기준의 선은 새로 오지만, 진 쪽 기준의 옛 선을 끊으라는 줄은 없다. `deleted` 를 받으면
   그 객체를 끝점으로 하는 선을 받는 쪽이 끊는다.
10. **참조 칸의 값은 보낼 때의 `key` 다.** 가리키는 쪽의 식별자가 나중에 바뀌어도 이미 받은 참조
    값은 다시 오지 않는다 — 옛 식별자로 남은 값은 `previous_keys` 로 풀어 찾는다. 가리키는 타입을
    먼저 받거나(`ref_type_slug`), 아직 없는 대상은 보류했다가 다시 푼다.
11. **404 는 두 가지다.** `APP-CORE-0001`(공개 안 된 타입 — 그 타입 수신을 멈추고 알린다)과
    `APP-CORE-0002`(커서를 못 읽음 — 커서 없이 지난 `as_of` 부터 다시 받는다). 상태 코드만 보고
    처리를 고르면 커서 문제 하나로 타입 수신을 통째로 멈춘다.

#### 선 가져오기 — 객체만 받으면 점만 있고 선이 없다

카탈로그의 `relations` 에 값이 있는 타입은 **그 타입에서 출발하는 선**도 같은 규칙으로 받는다.

```bash
curl -s "$SP/api/core/material/relations?since=$LAST_AS_OF&limit=500" \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "type_slug": "material",
  "as_of": "2026-09-22T02:00:00.000000Z",
  "next": null,
  "items": [
    { "src": "SS400", "relation": "supplies", "dst": "ACME-001", "dst_type": "vendor",
      "evidence_note": "계약서 3.2", "properties": { "n": 2 },
      "updated_at": "2026-09-21T08:11:00.123456Z", "deleted": false },
    { "src": "SS400", "relation": "supplies", "dst": "HAN-002", "dst_type": "vendor",
      "updated_at": "2026-09-22T01:00:00.000000Z", "deleted": true }
  ]
}
```

- 끝점은 **`key`** 로 온다(UUID 는 안 나간다). `dst_type` 은 도착점의 타입 slug 다 — 어느 표에서
  찾을지 알려 준다. **`key` 는 타입 안에서만 하나**라, 선은 `(src, relation, dst, dst_type)` 넷으로
  가린다(끝이 인터페이스인 종류는 같은 `dst` 가 두 타입에 있을 수 있다).
- `deleted: true` 는 **끊긴 선**이다. 선은 상태가 아니라 있음/없음이라, 받는 쪽도 끊는 편이 맞다.
- **양끝 객체의 타입이 모두 공개된 선만**, 그리고 **양 끝이 살아 있는 선만** 온다. 한쪽이 안
  열렸거나 지워졌으면 받는 쪽이 못 찾는 끝점을 쥐게 된다. 지운 객체의 선은 무덤 없이 빠지므로
  객체 무덤을 받으면 그 끝의 선을 받는 쪽이 끊는다(지킬 것 9). 관계 종류의 끝에 **인터페이스**(여러 타입이 따르는 공통 모양, ADR 0006)를 적었으면 그것을
  구현한 타입 중 **공개된 것**의 객체를 잇는 선만 온다 — 그래서 한 종류의 `dst_type` 이 선마다 다를
  수 있다. 무엇이 올 수 있는지는 카탈로그의 `relation_kinds[].dst[].types` 가 말하고, 구현 타입이 하나
  더 공개되면 `revision` 이 바뀐다. **기대한 관계가 안 오면** 공개 측에 코어 현황의 「제외된 관계」
  탭을 보아 달라고 한다 — 공개 타입에 닿지만 안 나가는 관계 종류와 그 이유(끝 타입 미공개 · 끝 타입
  미지정 등), 공개하면 나가는 타입이 거기 있다.
- `since` · `cursor` · `as_of` 규칙은 행과 **같다**(위의 「지킬 것」 이 그대로 적용된다).
  기준 시각은 **타입마다 · 행과 선을 따로** 적어 둔다.
- **유효 기간**(ADR 0039) — 관계 종류가 유효 기간을 받으면(카탈로그의 `relation_kinds[].effectivity`
  가 참) 선에 `valid_from`(시작일, 포함) · `valid_to`(끝날, **제외** — 그날부터 무효)가 `YYYY-MM-DD` 로
  실린다(비면 그쪽 끝이 열린 것). **이 창구는 오늘 유효한 선만 보낸다** — 그래서 같은
  `(src, relation, dst, dst_type)` 은 늘 한 줄이고, 받는 쪽의 선 키는 그대로 넷이다. 시계가 경계일을
  넘으면 그 일도 흐름에 든다(그날 0시가 그 일의 시각): 끝날이 지난 선은 `deleted: true` 로, 시작일이 온
  선은 살아 있는 선으로 — 같은 두 객체 사이에 다음 기간의 선이 그날 시작하면 끊김 대신 그 선이 온다. 지난
  기간의 선을 고치거나 지운 일, 앞으로의 선을 만든 일도 흐름에 들지만 늘 **그 선의 지금 상태**(오늘
  유효한 같은 선, 없으면 끊김)로 온다. 기간 두 칸은 「언제까지인가」 를 알려 주는 참고다 — 저장하지
  않아도 끊김이 제때 온다. 지난 · 예정 관계까지 통째로 받아야 하면 묶음(§6 · 4.4)이나 관계 내보내기(4.3)를
  쓴다(기간을 가리지 않고 전부 싣는다).
- **수량 칸**(ADR 0040) — 카탈로그의 `relation_kinds[].quantity_key` 가 비어 있지 않으면 그 종류의 선
  `properties` 에서 그 키가 「부모 하나에 자식 몇 개」(BOM 의 수량)다. 선의 모양은 그대로라 `revision` 이
  바뀌지 않는다. 받는 쪽이 전개(수량을 경로 따라 곱하기)를 직접 하려면 그 칸을 읽고, 칸이 없거나 숫자가 아닌
  선은 **1개**로 친다(SP 의 전개와 같은 뜻 — 0 은 0). SP 에서 전개한 표가 필요하면 `GET
  /api/objects/{타입}/{id}/explode`(정리 · 단계별 · 어디에 쓰였나)를 읽는다 — 코어 창구가 아니라 일반 API 다.
- **계보 관계**(ADR 0041) — 카탈로그의 `relation_kinds[].lineage_source` 가 `src` · `dst` 면 그 종류는 「무엇에서
  만들어졌나」 를 잇는 관계이고 그 끝이 **원천**(만드는 데 쓰인 것)이다(W3C PROV 의 `wasDerivedFrom` — 파생물 →
  원천). 선의 모양은 그대로라 `revision` 이 바뀌지 않는다. 선마다의 **고정**(맺을 때 원천의 개정 값)과
  **낡음**(원천이 그 뒤에 바뀌었나)은 이 창구로 나가지 않는다 — SP 안의 판정이다. 필요하면 `GET
  /api/objects/{타입}/{id}/lineage`(위 · 아래 사슬, 줄마다 낡음과 까닭)를, 낡은 것만 모으려면 목록 조건
  `f.lineage.eq=stale` 를 읽는다.
- **제안된 관계**(ADR 0042)는 **이 창구로 나가지 않는다** — 확정 전의 「이어야 할 것 같다」 는 선이 아니라 SP
  안의 작업 거리다(따로 둔 표라 선을 읽는 어느 자리에도 섞이지 않는다). 사람이 확정하는 순간 보통의 선이 되어
  그때부터 흐름에 든다(`updated_at` 이 그 시각). 묶음 내보내기 · RDF · 정의 내보내기에도 실리지 않는다.
- **`reset: true` 가 오면 `since` 를 비우고 처음부터 받는다.** 끊긴 선의 기록은 한동안만
  들고 있어서, 그보다 오래 안 받아 간 쪽에는 「그 사이에 무엇이 끊겼나」 를 말해 줄 수 없다 —
  그때 빈 쪽을 주면 받는 쪽은 「바뀐 것 없음」 으로 읽고 **끊긴 선을 영영 들고 있는다.** 다시 받은
  응답에도 끊긴 선은 없으므로, **끝까지 받은 뒤 이번에 안 온 선을 끊는다**(지킬 것 7).

#### 값의 표기 (온톨로지가 바뀌어도 안 바뀐다)

| | |
| --- | --- |
| 참조 칸 | 상대 객체의 **`key`**(`"ACME-001"`). UUID 는 안 나간다 |
| 여러 값 | **배열** (`["A","B"]`) |
| 날짜 · 일시 | `2026-09-22` · `2026-09-22T01:23:45.000000Z` |
| 빈 값 | 그 키가 **없다** |
| 별칭 | 있으면 `properties.aliases` 에 배열로. 없으면 키가 없다 |
| 바뀐 식별자 | `renamed_from` 에 **가장 마지막 옛 식별자**, `previous_keys` 에 **전부**(오래된 것부터). 오래 안 받아 갔으면 가진 것이 마지막 것이 아니다 |
| 첨부 | 안 나간다 |

#### 형제 Standard Platform 이면 코드가 없다

받는 쪽도 SP 면 위 반복문을 짤 일이 없다. **관리 › 데이터 소스 › 「형제 Standard Platform
(코어)」** 로 만들고 주소·토큰·수신할 코어 타입만 적으면 된다. 「대응 자동 제안」 이 이쪽
카탈로그를 읽어 칸을 이어 주고, 주기는 소스의 간격으로, 즉시 실행은 목록의 「동기화」 로 한다.

선(「선도 받기」)은 위 규칙을 그대로 지킨다 — `dst_type` 으로 도착을 그 타입에서만 찾고(끝이
인터페이스인 종류), `reset` 이 오면 전량을 다시 받아 **마지막 쪽까지 받은 실행에서** 상대에 없는
선을 끊는다. 5만 줄이 넘어 여러 실행에 걸쳐도 같다(도중에 실패한 실행은 아무것도 안 끊는다). 끊는
것은 **그 소스가 이은 선뿐**이다 — 사람이 화면에서 이은 선, 파일 · 다른 소스로 들어온 선은 안
건드린다. 한꺼번에 절반 넘게 안 오면 끊지 않고 실패로 적는다(상대 토큰으로 볼 수 있는 범위가 줄어든
경우를 막는다).

#### 더 빨라야 하면 — 웹훅으로 신호 받기

야간 1회로 모자라면 웹훅 수신구(§4.5)를 연다. SP 쪽에서 「코어 공개 타입만」 을 켜 두면
코어 타입이 바뀔 때마다 신호가 간다. **신호에는 값이 없다** — 「material 의 SS400 이 바뀌었다」
뿐이다. 받으면 위의 `GET /api/core/material?since=…` 를 부른다. 웹훅이 실패해도 야간 폴링이
받쳐 주므로, 둘은 경쟁이 아니라 짝이다.

#### 주기와 수동 실행

야간 1회로 시작하고, **수동 실행 버튼을 반드시 함께 둔다** — 새벽에 실패했을 때 다음 날까지
기다리게 하면 안 된다. 더 빨라야 하면 웹훅(§4.5)으로 신호를 받아 그때 이 길을 부른다.

### 4.2b 길 ①-b 타입 하나를 쪽 단위로 (코어가 아닌 것)

```
GET /api/objects/{type_slug}?limit=200&offset=0
```

```json
{
  "items": [
    {
      "id": "0f2c...",
      "type_slug": "supplier",
      "key": "ACME-001",
      "label": "ACME 정밀",
      "description": "",
      "properties": { "grade": "1등급", "country": "KR" },
      "ref_labels": { "3a1e...": "탄소강" },
      "aliases": ["앤시스"],
      "external_ids": { "erp": "V-100" },
      "status": "active",
      "owner_workspace_slug": "hq",
      "owner_workspace_name": "본사",
      "valid_from_year": null,
      "valid_to_year": null,
      "created_at": "2026-01-02T03:04:05Z",
      "updated_at": "2026-09-01T00:00:00Z"
    }
  ],
  "total": 1234, "limit": 200, "offset": 0
}
```

주의 두 가지:

- **참조 칸의 값은 UUID 다.** 사람이 읽을 이름은 같은 응답의 `ref_labels` 에 `{UUID: 이름}` 으로
  따로 온다. 그쪽이 이름을 저장할 것이면 여기서 꺼낸다.
- `total` 을 믿고 `offset` 을 끝까지 돌린다. 한 쪽의 상한은 서버가 강제한다 — 기본 50, 최대 200.

**상대의 값까지 한 번에 — 이어진 칸**(ADR 0043). 「제품마다 기본 모델 이름」 처럼 다른 객체의 값이 필요하면
줄마다 `GET /api/objects/{type}/{id}` 를 부르지 말고 `columns` 를 준다(조건과 같은 주소, 열까지):

```
GET /api/objects/plm_model?limit=200&columns=out.sku_base.label&columns=in.svc_case:model
```

```json
{
  "items": [ ... ],
  "linked_columns": [
    {"field": "out.sku_base.label", "label": "기본 모델 › 이름", "data_type": "text", "multi": false},
    {"field": "in.svc_case:model", "label": "가리키는 것 · 서비스 기록(개발모델)", "data_type": "object", "multi": true}
  ],
  "linked": {
    "0f2c...": {
      "out.sku_base.label": {"values": [{"value": "B-100", "label": "B-100"}], "more": false},
      "in.svc_case:model": {"values": [{"value": "9a1c...", "label": "C0012345"}, ...], "more": true}
    }
  }
}
```

칸마다 **20개까지**, 넘으면 `more: true`(몇 개인지는 세지 않는다 — 수는 `/summary`). 이어진 것마다 값 하나라
같은 값이 여러 번 올 수 있다. 객체를 가리키는 값은 `value` 가 UUID, `label` 이 이름이다. 볼 수 없는 객체는
걷지 않는다. **선의 칸**(관계 속성 — BOM 의 수량)도 주소가 있다: `out.<관계>~<관계 속성>`. 조건에서 같은 선 하나에
함께 맞아야 하는 조건은 `fe<번호>.<칸>.<연산>=<값>` 으로 묶는다(안 묶으면 조건마다 「이어진 것 중 하나라도」).

### 4.3 길 ② 파일로 통째 (큰 타입)

큰 타입은 쪽을 돌리지 말고 파일로 받는다. **작업**이라 세 걸음이다.

```bash
# 1) 넣는다 — 202 와 작업 id
curl -sX POST "$SP/api/objects/supplier/export?format=json" -H "Authorization: Bearer $TOKEN"
# {"id":"9d1f...","status":"queued",...}

# 2) 될 때까지 본다 — status 가 done 이 될 때까지 몇 초 간격으로
curl -s "$SP/api/jobs/9d1f..." -H "Authorization: Bearer $TOKEN"

# 3) 받는다
curl -s "$SP/api/jobs/9d1f.../download" -H "Authorization: Bearer $TOKEN" -o supplier.json
```

- `status` 는 `queued` · `running` · `done` · `failed` · `cancelled`.
- `failed` 면 `error` 에 이유가 한 줄로 온다.
- 목록과 **같은 거르개**를 쿼리로 붙일 수 있다 — `?status=active&p.grade=1등급`.
- 관계는 `POST /api/objects/{type_slug}/relations/export?format=json`.

### 4.4 길 ③ 정의까지 통째 (쌍둥이용)

SP 쌍둥이처럼 **같은 구조를 그대로 받는** 경우에는 묶음을 받는다.

```bash
curl -sX POST "$SP/api/bundles/export" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"group":"plm"}'
# → 작업. 4.3 과 같은 방식으로 받는다. 받은 JSON 이 §6 의 묶음이다.
```

받은 묶음을 그대로 자기 SP 에 넣으면 정의·객체·관계가 한 번에 선다(§5).

> 정의까지 받으려면 시스템 관리자 토큰이 필요하다 — 부서를 가리지 않고 전부 나가기 때문이다.

### 4.5 즉시 알림이 필요하면 — 웹훅 수신구 (선택)

주기 폴링으로 충분하면 안 만들어도 된다. 「바뀐 순간」 이 필요하면 엔드포인트 하나를 연다.

SP 쪽에서는 시스템 관리자가 **관리 › 웹훅**에 그쪽 주소 · 서명 비밀 · 이벤트(`object.*`)를 적고
「코어 공개 타입만」 을 켠다.

```
POST {그쪽 주소}
Content-Type: application/json; charset=utf-8
X-Event: object.update
X-Delivery-Id: 6b2f...
X-Signature-256: sha256=9f86d0...
User-Agent: standard-platform-webhook
```

```json
{
  "id": "6b2f...",
  "event": "object.update",
  "at": "2026-09-22T01:23:45.000000+00:00",
  "actor": { "label": "홍길동", "client": "web", "token": null },
  "target": { "table": "objects", "id": "0f2c...", "label": "ACME 정밀", "type_slug": "supplier" },
  "workspace_id": "1a2b...",
  "changes": { "label": ["ACME", "ACME 정밀"] },
  "reason": "",
  "request_id": "3f2c..."
}
```

이벤트 이름은 감사 기록의 이름 그대로다 — 객체는 `object.create` · `object.update` · `object.delete`
· `object.merge` · `object.restore`, 선은 `object.relation.add` · `object.relation.update` ·
`object.relation.remove`(이때 `type_slug` 는 **출발 객체**의 타입), 정의는 `ontology.*`(`type_slug`
없음). `object.changed` 라는 이벤트는 없다 — 그것은 SP 안의 알림 종류다(이 문서의 0.4.15 판 예시가
그것을 잘못 적었다).

받는 쪽 규칙:

1. **서명을 확인한다** — `X-Signature-256` 은 `"sha256=" + HMAC-SHA256(secret, 원문 바이트)`.
   비교는 상수 시간 비교 함수로. 서명이 다르면 401 로 돌려보낸다. 서명 비밀을 비워 두면 SP 는
   서명하지 않는다 — 비워 두지 않는다.
2. **2xx 를 빨리 돌려준다.** 본문은 안 봐도 된다. SP 는 10초 기다리고, 느리면 재시도가 쌓인다.
3. **같은 것이 두 번 올 수 있다.** `X-Delivery-Id` 를 저장해 두고 이미 본 것은 버린다.
4. **이 알림으로 값을 반영하지 않는다.** 「무엇이 바뀌었다」 의 신호로만 쓴다 — 받으면 `type_slug`
   의 §4.2/4.3 으로 끌어가 확인한다. `changes` 는 감사 기록의 차이라 사람이 읽는 것이고,
   `target.id` 는 SP 내부 id 다. 그것으로 반영하면 받는 쪽마다 다른 시점의 값을 갖게 된다.
   `ontology.*` 가 오면 카탈로그를 다시 읽는다.
5. 실패하면 SP 가 **첫 시도를 포함해 세 번까지** 보낸다. 그 뒤에는 SP 화면에서 사람이 다시
   보낸다 — 그래서 웹훅을 써도 야간 폴링은 끄지 않는다.

## 5. 그쪽이 SP 로 밀어 넣기 (선택)

읽어 가는 쪽으로 충분하면 안 해도 된다. 그쪽이 「내가 보낼 때 보내겠다」 면 이 길이다.

```bash
# 1) 미리 보기 — 아무것도 저장하지 않는다
curl -sX POST "$SP/api/bundles/import" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"source":"matnexus","apply":false,"objects":[{"type_slug":"supplier","rows":[...]}]}'
# → 202, 작업 id

# 2) 계획을 본다 — 행마다 create · update · unchanged · error
curl -s "$SP/api/jobs/{id}" -H "Authorization: Bearer $TOKEN"

# 3) 넣는다 — 같은 파일, 같은 지문
curl -sX POST "$SP/api/jobs/{id}/apply" -H "Authorization: Bearer $TOKEN"
```

- `apply: true` 로 한 번에 보내도 된다. 그때도 **전부 아니면 무**다 — 한 행이 오류면 아무것도 안 들어간다.
- `source` 는 그쪽 시스템 이름(소문자·숫자·`-`·`_`, 40자 이내). 이것이 있어야 「그쪽이 관리하는
  것」 으로 표시되고, SP 화면에서 사람이 손대는 것을 막는다 — 안 막으면 다음 동기화가 그 수정을
  말없이 덮어쓴다.
- **막히는 것은 손으로 고치는 것뿐이다.** 같은 `source` 를 말하는 적재는 그대로 통과한다 —
  이 이름을 다시 말하지 못하면 「받기」 까지 막힌다. 받는 쪽이 데이터 소스로 당겨 오는
  방식이면 그 소스의 **「출처 이름」** 을 이 값과 같게 적는다(비우면 소스의 slug 를 쓴다).
- 정의(`ontology`)가 든 묶음은 `ontology:write` 범위가 더 필요하다.

### 5.1 확실하지 않은 관계는 제안으로 — `POST /api/objects/relation-proposals`

그쪽(또는 그쪽의 AI · 규칙 엔진)이 **추론하거나 추출한** 관계 — 「이 고장 보고는 이 부품 이야기 같다」 — 를 묶음으로
밀어 넣으면 확정 안 된 선이 SP 의 트리 · 지표 · 코어 창구에 섞인다. 그런 것은 **제안**으로 보낸다(ADR 0042).
사람이 SP 의 검토함 「제안된 관계」 에서 확정해야 선이 된다.

```bash
curl -sX POST "$SP/api/objects/relation-proposals" -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"rows":[{"src_object_id":"<id>","relation":"fails_by","dst_object_id":"<id>",
                   "confidence":0.82,"evidence_note":"FMEA 시트 12행 — 원인 칸",
                   "origin":"rule","origin_ref":"matnexus-fmea-2026Q3"}]}'
# → 200, 줄마다 status: created · open · connected · rejected_before · error
```

- 한 번에 500줄, **줄마다 결과**(한 줄이 틀려도 나머지는 남는다 — 묶음과 다르다). 양 끝은 SP 의 객체 id
  (이름이면 `resolve-many` 로 먼저 푼다). 부서 · 계정으로 가는 선은 받지 않는다.
- `connected` — 같은 선이 이미 있다. `open` — 같은 제안이 열려 있다(더 높은 `confidence` 면 근거 · 확신도를 바꾼다).
  `rejected_before` — **사람이 거절한 적 있다**(메시지에 언제 · 누가 · 까닭). 같은 것을 매번 다시 보내도 되도록
  만들어 두었다 — 거절된 것은 `"again": true` 를 줄 때만 다시 열린다.
- `origin` 은 `user` · `mcp` · `rule` · `datasource` · `import`, `origin_ref` 는 그쪽 시스템 · 작업 이름(검토함이 같은
  출처를 한 줄로 묶는다). 범위는 `objects:write`, 권한은 **양 끝을 볼 수 있는가**뿐이다(확정은 SP 의 사람이).
- 지금 상태를 읽으려면 `GET /api/objects/relation-proposals?status=&origin=&relation=`(쪽 넘김, `read`).

```json
{
  "format": "sp-bundle/1",
  "group": "plm",
  "exported_at": "2026-09-22T01:23:45Z",
  "ontology": { "groups": [...], "types": [...], "relation_types": [...] },
  "objects":  [ { "type_slug": "supplier", "workspace_slug": null, "rows": [ ... ],
                  "aliases_mode": "add" } ],
  "relations":[ { "type_slug": "part", "rows": [ ... ], "mode": "add" } ],
  "tombstones": { "objects": [ ... ], "relations": [ ... ] },
  "counts": { "types": 4, "objects": 1200, "relations": 300, "tombstones": 2 },
  "warnings": []
}
```

넣을 때는 `ontology` · `objects` · `relations` · `tombstones` · `source` · `apply` 만 쓴다.
나머지는 무시된다. **하나만 보내도 된다** — 객체만 보내려면 `ontology` 를 아예 빼면 된다.

### 6.0 대량 적재(백필)에 쓰는 네 칸

수만 줄을 한 번에 넣을 때는 기본값이 발목을 잡는다. 넷을 함께 켠다.

| 칸 | 기본 | 백필 | 왜 |
| --- | --- | --- | --- |
| `preview` | `full` | `plan` | 기본은 적용을 끝까지 돌린 뒤 되돌린다(판정이 적용과 같다) — **시간이 두 배**다. `plan` 은 계획만 보고, 이 묶음이 만들 것을 가리키는 칸은 「적용할 때 풀린다」 로 줄에 적는다 |
| `events` | `each` | `summary` | 줄마다 웹훅이 나가면 수신 측이 수만 번 두드려 맞고, 그때 받는 쪽은 무슨 일인지 알 수 없다 |
| `audit` | `each` | `summary` | 백필 수만 줄이 감사 로그를 뒤덮으면 사람이 한 일을 그 사이에서 못 찾는다 |
| `missing_refs` | `error` | `blank` | 기본은 전부 아니면 무다 — **한 줄이 묶음 전체를 막는다.** `blank` 는 그 칸만 비우고 줄에 적는다(선은 그 줄을 건너뛴다) |

`summary` 를 켜면 **묶음 한 줄**은 반드시 남는다(`bundle.import`) — 무엇이 몇 건인지 그 줄이
말한다. 아무것도 안 남기는 길은 없다.

### 6.1 정의 (`ontology`)

| 자리 | 필수 칸 | 자주 쓰는 칸 |
| --- | --- | --- |
| `groups[]` | `slug`, `label` | `icon`, `parent_slug`(상위 묶음), `color`(그래프 색 `#rrggbb` — 비우면 순서대로), `sort_order`, `is_active` |
| `interfaces[]` | `slug`, `label` | `extends_slugs`, `description`, `properties[]`(공통 속성) |
| `types[]` | `slug`, `label` | `nav_group_slug`, `interface_slugs`, `key_policy`, `description`, `properties[]` |
| `types[].properties[]` | `key`, `label`, `data_type` | `required`, `multi`, `unit`, `enum_options`, `ref_type_slug`, `help`, `default_value`, `unique` |
| `relation_types[]` | `slug`, `label`, `src_type_slugs`, `dst_type_slugs` | `inverse_label`, `directed`, `cardinality` |

`data_type` 은 열 중 하나: `text` · `text_long` · `number` · `date` · `datetime` · `bool` ·
`enum` · `url` · `object_ref` · `file`.

**인터페이스**(ADR 0006)는 여러 타입이 따르는 공통 모양이다. 타입이 `interface_slugs` 로 구현하면
공통 속성을 **같은 키 · 같은 모양**으로 갖는다 — 같은 키에 모양이 다른 속성이 있으면 거절된다.
타입의 `parent_slug`(옛 상위 타입)는 없어졌다 — 보내면 거절된다.
`enum` 이면 `enum_options` 가, `object_ref` 면 `ref_type_slug` 가 있어야 한다.
파일 칸(`file`)은 **묶음으로 오가지 않는다.**

**보낸 칸만 바뀐다.** 안 적은 칸은 그대로 둔다 — 그래서 일부만 보내도 안전하다.

### 6.2 객체 행 (`objects[].rows[]`)

고정 칸 + 속성 키를 **한 평면**에 적는다.

```json
{
  "key": "ACME-001",
  "label": "ACME 정밀",
  "description": "",
  "aliases": "앤시스;ANSYS",
  "status": "active",
  "valid_from_year": 2024,
  "valid_to_year": null,
  "grade": "1등급",
  "material": "SS400"
}
```

| 칸 | 규칙 |
| --- | --- |
| `key` | 있으면 이것으로 찾아 **고친다**(upsert). 없으면 `label` 로 찾는다 |
| `label` | 필수. 사람이 읽는 이름 |
| `status` | `active` · `deprecated`. **지우지 말고 `deprecated`** |
| `aliases` | 여러 개는 배열로(`["갈라짐; 크랙"]`). 글 하나로 주면 `;` 로 쪼갠다 |
| `renamed_from` | **옛 식별자.** 키 체계가 바뀔 때 이것으로 찾아 `key` 로 바꾸고, 옛 것은 별칭으로 남는다 |
| `aliases_mode` | 배치 단위. 기본 `add`(더하기), `replace` 면 **파일에 없는 별칭을 지운다** |
| 속성 | 속성 `key` 를 열 이름으로. 여러 값도 `;` 로 |
| 참조 속성 | **상대 객체의 `key`**(없으면 이름)를 적는다. UUID 를 적지 않는다 |
| 값 비우기 | 빈 문자열은 「안 보냄」 이다. **지우려면 `\null`** 을 적는다 |
| 한 덩이 | 한 배치 5,000행. 넘으면 배치를 나눠 적는다 |

`objects` 는 **적은 차례대로** 들어간다. 다른 타입을 참조하는 타입은 그 뒤에 둔다.

### 6.3 관계 행 (`relations[].rows[]`)

```json
{
  "src": "PART-1", "relation": "supplied_by", "dst": "ACME-001",
  "evidence_note": "계약서 3.2",
  "properties": { "n": 3, "basis": "시험" }
}
```

- `type_slug` 는 **출발 타입**이다. `src` 는 그 타입의 객체여야 한다.
- `src` · `dst` 는 상대의 `key`(없으면 이름·별칭). 이름이 여럿에 맞으면 그 행은 오류다.
- `valid_from` · `valid_to`(`YYYY-MM-DD`, 끝날은 제외) — **유효 기간을 받는 관계 종류의 줄만**(ADR
  0039). 같은 세 끝도 기간이 겹치지 않으면 여럿이다. 기간이 같은 선이 있으면 그 선, 기간이 겹치는 선이
  하나 있으면 그 선의 기간을 고친다(둘 이상과 겹치면 그 행은 오류). `mode: "replace"` 는 **기간까지가 선의
  정체**라 묶음에 없는 기간의 선을 끊는다.
- `pinned_revision` · `pinned_at` · `pinned_stale` — **계보 관계 종류의 줄만**(ADR 0041), 허브의 묶음 내보내기가
  싣는다. 실려 오면 새로 박지 않고 그 고정(「Rev.C 기준」)을 그대로 쓴다 — 있는 선은 뜻이 다를 때만(개정 칸이
  있으면 고정 개정이, 없으면 낡음 판정이) 고친다. 원천 타입에 개정 칸이 없는 선은 고정 시각이 보낸 쪽의
  시계라, 받는 쪽은 시각 대신 **판정**(`pinned_stale` — 보낸 쪽에서 낡았나)을 옮긴다. 안 실으면 맺는 순간 이
  설치의 값이 박힌다.
- **관계에 붙은 속성**은 `properties` 로 보낸다(CSV 에서는 속성 `key` 를 열 이름으로).
  모양은 **관계 종류의 속성 정의**로 검사한다 — 정의에 없는 키는 그 행이 오류다.
- 세 끝이 같은 줄을 다시 보내면 **근거·속성이 다를 때만 「고침」** 이다.

### 6.4 사라진 것 (`tombstones`)

허브에서 **지운 객체와 끊긴 선**이다. 예전에는 아무것도 가지 않아, 허브에서 지운 것이 받는
쪽에 살아 남았다(코어 API 는 같은 사실을 이미 `deleted` · `merged_into` 로 말하고 있었으니,
**두 길이 다르게 움직인 것**이 더 나쁜 쪽이다).

```json
{
  "objects": [
    { "type_slug": "task", "key": "T-2", "merged_into": null },
    { "type_slug": "model", "key": "M-2", "merged_into": "M-1" }
  ],
  "relations": [
    { "type_slug": "model", "src": "M-2", "relation": "derived_from", "dst": "M-1" },
    { "type_slug": "part", "src": "A1", "relation": "bom_of", "dst": "P",
      "valid_from": null, "valid_to": "2026-03-01", "period": true }
  ]
}
```

끊긴 선에 `period: true` 가 있으면 `valid_from` · `valid_to` 가 **그 선의 기간**이다(둘 다 null 이면 「늘
유효한 선」) — 받는 쪽은 그 기간의 선만 끊는다. 같은 두 객체 사이에 기간을 달리한 선이 여럿일 수
있어서다(ADR 0039). `period` 가 없으면(예전 묶음 · 코어 창구의 끊김) **오늘 유효한 그 선**을 끊는다.

**받는 쪽은 지우지 않는다.**

| 온 것 | 받는 쪽이 하는 일 | 계획의 말 |
| --- | --- | --- |
| 객체, `merged_into` 없음 | **사용 중지**(`deprecated`) — 이쪽에서 그것을 가리키는 것이 있다 | `deprecate` |
| 객체, `merged_into` 있음 | **합치기** — 이쪽의 참조 · 관계가 이긴 쪽으로 옮겨진다 | `merge` |
| 선 | **끊기** — 선은 상태가 아니라 있음/없음이다 | `unlink` |
| 이미 그렇게 된 것 | 아무것도 안 한다 | `unchanged` |
| 합칠 자리(이긴 쪽)가 이쪽에 없음 | 그 줄만 오류 — 이긴 쪽을 먼저 받는다 | `error` |

무덤은 **맨 뒤에** 처리된다. 합치기는 이긴 쪽이 이미 있어야 하고, 그것은 같은 묶음의 객체
단계가 넣기 때문이다.

**무덤은 `source` 가 붙은 묶음에만 있다**(시스템 관리자). 아무나 보낼 수 있으면 남의 전역
객체를 사용 중지 · 합치기 · 끊기 할 수 있다 — 줄마다 그 객체를 고칠 수 있는지도 다시 본다.

보내는 쪽은 **살아 있는 것과 겹치는 무덤을 빼고** 보낸다. 무덤은 식별자와 세 끝으로만
말하므로, 같은 식별자를 다시 만들거나 같은 선을 다시 이으면 받는 쪽에서 옛 무덤과 새것이
구별되지 않는다 — 방금 받은 것을 그 자리에서 다시 지우게 된다.

## 7. 공통 규약

| 것 | 규약 |
| --- | --- |
| 시각 | ISO-8601 UTC, `Z` 붙임. `2026-09-22T01:23:45Z` |
| 날짜 | `2026-09-22` |
| 불리언 | JSON `true`/`false`. 문자열이면 `true/1/y/yes/예/참/o` 를 참으로 읽는다 |
| 숫자 | JSON 숫자. 단위는 값에 섞지 않는다(`"12 mm"` ✗, `12` ✓ — 단위는 정의에 있다) |
| 빈 값 | `null` 또는 생략 = 「안 보냄」. **지우기는 `\null`** |
| 여러 값 | `;` 로 이어 적는다 |
| 인코딩 | UTF-8. CSV 로 주고받을 일이 있으면 BOM 없이 |
| 대소문자 | `slug` · `key` 는 **그대로** 비교한다 |

## 8. 오류

SP 의 오류는 언제나 같은 봉투다.

```json
{ "error": { "code": "APP-OBJECTS-0046", "message": "「ACME」 식별자가 2개 타입에 있습니다.",
             "request_id": "3f2c...", "details": {} } }
```

- **`message` 를 그대로 사람에게 보여 준다.** 우리말 한 줄로 「무엇이 왜 막혔나」 가 들어 있다.
- `request_id` 를 로그에 남긴다 — SP 쪽 로그와 맞대 볼 때 이것으로 찾는다.
- 재시도: `5xx` 와 네트워크 오류만. `4xx` 는 다시 보내도 같다(`429` 는 예외 — 기다렸다 한 번 더).
- `401` · `403` 이면 토큰이나 범위 문제다. 내보내기가 403 이면 §4.1 의 범위를 확인한다.

## 9. curl 자가 점검

그쪽이 만든 것이 맞는지 **SP 없이** 확인하는 순서다.

```bash
BASE=https://your-system.example.com
TOKEN=...

# 1) 인증 없이 부르면 막히나 (막혀야 한다)
curl -si "$BASE/api/suppliers?page=1&page_size=2" | head -1        # → 401

# 2) 첫 쪽이 오나
curl -s "$BASE/api/suppliers?page=1&page_size=2" -H "Authorization: Bearer $TOKEN" | jq .

# 3) 행이 있는 자리가 언제나 같나 (items 든 data 든 하나로 고정)
curl -s ... | jq '.items | length'

# 4) 식별자가 비어 있지 않나
curl -s ... | jq '[.items[] | select(.id == null or .id == "")] | length'   # → 0

# 5) 두 번 부르면 같은 순서인가
diff <(curl -s "...page=1" | jq -r '.items[].id') \
     <(curl -s "...page=1" | jq -r '.items[].id')                    # → 차이 없음

# 6) 마지막 쪽이 덜 차나 (끝을 알 수 있나)
curl -s "...page=999" | jq '.items | length'                          # → 0

# 7) 지운 것이 행으로 남아 있나
curl -s "..." | jq '[.items[] | select(.is_active == false)] | length' # → 0 이 아니어야 정상
```

SP 쪽으로 받아 가는 것은 §4.3 의 세 줄을 그대로 돌려 보면 된다.

## 10. 자주 틀리는 것

1. **식별자를 바꾼다** — 시스템 개편 때 코드 체계를 갈아엎으면 SP 에 같은 것이 둘 생긴다. 바꿔야
   하면 **먼저 알려 주고**, 옛 식별자를 별칭으로 남긴다.
2. **지운 행을 목록에서 뺀다** — SP 는 「안 온 것」 과 「지운 것」 을 구별할 수 없다. §2-3.
3. **참조를 UUID 로 적는다** — 묶음에서는 상대의 `key` 를 적는다. UUID 는 설치마다 다르다.
4. **빈 문자열로 지우려 한다** — 빈 값은 「안 보냄」 이다. 지우기는 `\null`.
5. **쪽 넘김 중에 정렬이 바뀐다** — 행이 빠지거나 두 번 온다. 정렬을 식별자로 고정한다.
6. **시각에 타임존이 없다** — 「어제 것」 인지 「오늘 것」 인지 못 정한다.
7. **새 코드값을 말없이 늘린다** — SP 의 고를 값에 없는 코드는 그 행을 오류로 만든다. §12-B ③.
8. **웹훅 본문의 값을 그대로 저장한다** — 알림은 「바뀌었다」 는 신호다. 값은 끌어가서 확인한다.
9. **웹훅을 동기로 오래 처리한다** — 큐에 넣고 2xx 를 먼저 돌려준다.
10. **쓰기 토큰으로 읽기만 한다** — 받아만 가면 `read` 로 충분하다. 넓은 토큰은 사고의 크기를 키운다.

## 11. 체크리스트

**그쪽 → SP (§3)**

- [ ] 읽기 엔드포인트 하나 (JSON, 평평한 항목)
- [ ] 안 바뀌는 식별자 · `updated_at` · 사용 중지 표시
- [ ] 쪽 넘김 한 가지 + 마지막 쪽을 알 수 있음
- [ ] 읽기 전용 토큰 발급
- [ ] §9 의 7가지 점검 통과
- [ ] 열 이름 목록과 코드값 목록을 문서로 전달

**SP → 그쪽 (§4)**

- [ ] SP 관리자에게 토큰 받기 — 코어만 받아 갈 것이면 `core:read`
- [ ] 연동 키트의 `check.sh` 통과 (인증 거부 · 카탈로그 · 첫 쪽)
- [ ] 타입 이름·칸 이름을 카탈로그에서 읽는다 (코드에 박지 않는다)
- [ ] `key` 를 그쪽 DB 에 저장 — 다음 수신이 「새로 만들기」 가 아니라 「고침」 이 되게
- [ ] `as_of` 는 **끝까지 받은 뒤에만** 저장. `next` 가 남아 있으면 저장하지 않는다
- [ ] `deleted` · `merged_into` 처리 (지우지 말고 사용 중지)
- [ ] 받아 온 타입은 그쪽 화면에서 **읽기 전용** (§12-A 2)
- [ ] 수동 실행 경로 — 새벽에 실패했을 때 다음 날까지 기다리지 않게
- [ ] 오류 봉투의 `message` · `request_id` 로그
- [ ] 첫 적재 뒤 건수·표본 대조를 **주기를 켜기 전에**
- [ ] (선택) 웹훅 수신구 + 서명 확인 + 멱등 처리

## 12. 규약과 양식

### 12-A. 확정된 것 — 시스템마다 다시 정하지 않는다

| # | 물음 | 확정 |
| --- | --- | --- |
| 1 | 주기 | **야간 1회 + 수동 실행 경로를 함께 둔다.** 즉시성이 필요한 타입만 웹훅(§4.5)을 덧댄다 |
| 2 | 충돌하면 누가 이기나 | **공개한 쪽이 이긴다.** 수신 측은 받아 온 타입을 자기 화면에서 **읽기 전용**으로 잠근다. 양쪽에서 고칠 수 있게 두면 다음 수신이 한쪽 수정을 말없이 덮는다 |
| 3 | 증분 | **구현되어 있다** — `since` + `cursor` + 삭제 표식(§4.2). `since` 에는 **서버가 준 `as_of` 를 그대로** 넣는다. 그쪽 시계로 만들면 그 사이 행이 새고, 샌 줄은 아무도 모른다 |
| 4 | 삭제 | 행을 목록에서 빼지 않는다. 그만 쓰는 것은 `status: "deprecated"`, 사라진 것은 `deleted: true`(합쳐졌으면 `merged_into`)로 알린다 |
| 5 | 첫 적재 | 전량 한 번 → 건수·표본 대조 → 주기 켜기. 대조 전에 주기를 켜면 틀린 대응이 이력에 쌓인다 |
| 6 | 토큰 | **시스템마다 따로.** 코어만 받아 가면 `core:read` 하나. 한 곳을 끊어도 나머지가 살아 있게 |
| 7 | 모르는 칸 | 무시한다. 공개 측이 칸을 늘려도 수신 측이 안 깨지는 이유가 이것이다 |
| 8 | 시각 | ISO-8601 UTC(`Z`). 로컬 시각·오프셋 없는 문자열은 받지 않는다 |
| 9 | 식별자 | 보내는 쪽이 정하고 **절대 바꾸지 않는다.** 바꿔야 하면 먼저 알리고 옛 식별자를 별칭으로 남긴다 |
| 10 | 대조할 자리 | 공개 측의 **코어 › 「최근 조회 이력」**(`core.pull`)과 수신 측 로그. 막혔을 때 이 둘을 맞대 본다 |

### 12-B. 시스템마다 채울 것 — 연동 전 교환할 양식

아래 넷을 채워 양쪽이 같은 사본을 갖는다. **빈칸으로 남은 항목은 연동을 켜지 않는 사유다.**

**① 대상 타입**

| SP 공개 타입 | 수신 측 저장 위치 | 식별자 대응 | 첫 적재 예정일 |
| --- | --- | --- | --- |
| `` | | SP `key` ↔ | |
| `` | | SP `key` ↔ | |

칸 대응은 표로 적지 않아도 된다 — 카탈로그(`GET /api/core`)가 칸 목록·자료형·단위·고를 값을
이미 말한다. 형제 SP 면 데이터 소스의 「대응 자동 제안」 이 그것을 읽어 채운다.

**② 시각과 실행**

| 것 | 값 |
| --- | --- |
| 야간 수신 시각 | (예: 01:00 KST) |
| 수동 실행 경로 | (수신 측의 화면 또는 명령) |
| 웹훅 | 사용 / 미사용 — 사용하면 수신구 주소와 서명 비밀을 주고받는 방법 |
| 재시도 | 실패 시 몇 번, 그 뒤에 누구에게 알리나 |

**③ 코드값 (고를 값)**

| 타입 · 칸 | 지금의 값 | 늘릴 때 알리는 사람·방법 | 유예 |
