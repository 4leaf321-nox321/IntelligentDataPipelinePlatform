# 0001. 레거시 시스템과 Standard Platform 사이의 중계 플랫폼 — 허브 앞단에 서고, SP 틀을 포크한다

- 상태: 채택
- 날짜: 2026-11-05
- 관련: StandardPlatform `docs/외부-시스템-연동-지침서.md`(사본 [docs/sp/](../sp/외부-시스템-연동-지침서.md)),
  SimEngBay ADR 0005(SP 를 포크하되 온톨로지는 가져오지 않는다), ReportArchive `[미구현] 기준정보_교환_설계.md`

## 배경

PLM · MES 같은 레거시 시스템의 데이터를 Standard Platform(SP) 인스턴스들에 넣어 왔다. 지금 흐름은
이렇다:

    사람이 PC 에서 PLM API 호출 → 로컬에 저장 → AI(Claude Code)로 온톨로지 모양으로 가공
    → sp_pipeline(validate · preview · apply) 으로 넣기

아픈 곳은 AI 가 아니라 그 앞뒤에 있었다.

- `sp_table.py`(`sp-table/1` — 행마다 AI 가 판단하지 않는 규칙 변환)는 **CSV 만** 읽는다. 그래서
  API 의 JSON 은 매번 AI 가 가공한다. 결과가 매번 다르고, 느리고, 사람이 붙어 있어야 한다.
- 실행이 **사람과 PC 에 묶여 있다.** PLM 데이터가 개인 PC 에 남는다.
- 매번 전체 스냅샷이다. `sp_table` 은 무덤(`tombstones`)을 만들지 않으므로 **원천에서 지운 것을
  알릴 길이 없다.**
- 실행 폴더가 일회성이라 「무엇을 어디서 받아 어디로」 가 등록된 것으로 남지 않는다.

## 결정

### 1. 무엇을 하나 — 레거시 → SP 의 입구

**레거시 시스템의 데이터를 매일 받아, 정해 둔 규칙(레시피)으로 SP 온톨로지 모양으로 바꿔, 맞는
데이터허브에 넣는다. 그리고 그 연결을 한눈에 보여 준다.**

| 원천(정본) | 받는 곳 | 그다음 |
| --- | --- | --- |
| PLM(과제 · 개발모델 …) | **자주검증 Datahub**(SP 인스턴스) | Datahub 가 코어 API 로 다른 SP 에 뿌린다 |
| MES(제조 데이터) | **제조 데이터허브**(SP 인스턴스) | 필요하면 그 허브가 뿌린다 |
| 그 밖의 레거시 | 그 데이터를 받을 허브 | — |

하지 않는 것:

- **정본이 아니다.** 정본은 PLM · MES 다. 받는 쪽에서는 `source`(`plm` · `mes`)가 붙어 사람이 손으로
  못 고친다.
- **다른 플랫폼에 뿌리지 않는다.** 그것은 허브가 한다. 원천의 한 타입은 **허브 한 곳으로만** 간다 —
  relay 가 같은 타입을 다른 SP 에 직접 보내면 그 인스턴스에 출처가 둘이 되고 `source` 잠금이
  부딪힌다. ReportArchive 의 「새 교환 시스템 신설 금지 · N:N 금지」 는 플랫폼끼리의 교환을 막는
  것이고, 이 플랫폼은 바깥 원천에서 SP 로 들어오는 입구라 그와 부딪히지 않는다.
- **기준정보를 만들지 않는다.** 부서 · 인원 · 설비 · 코드는 SP 의 대표 플랫폼이 뿌린다. relay 는 key
  로 참조만 하고, 대상에 아직 없는 참조는 그 줄만 보류했다가 다음 실행에서 다시 푼다.
- **레거시에 다시 쓰지 않는다.** 원천 쪽은 읽기 전용이다.

### 2. 어떻게 — AI 는 레시피를 짓고, 규칙이 매일 돈다

    [수집기 — relay_core, 서버 타이머]
      원천 어댑터 ── PLM API │ 중간 시스템 │ 파일
           ▼  변경분(since) + 삭제 표시
      미러(원천 키마다 최신 행, 원본 보관)
           ▼
      레시피 실행 — sp_table.convert() 를 그대로
           ▼
      (규칙이 못 푼 줄만) GLM 보강 → 미해결 · 관계 제안 · 미확인 별칭
           ▼
      지난번 **적용된** 출력과 비교 → 바뀐 줄 + tombstones.json
           ▼
      sp_pipeline validate → preview(대상 SP, source) → 그 허브의 검토함 「적용 대기 계획」
    ─────────────────────────────────────────────────────────────
    [SP 인스턴스 — 통제판]  사람이 적용(안정되면 기준 충족 시 자동) · 되돌리기 · 감사 · 배포

- **변환은 늘 미러 전체를 다시 한다.** 레시피는 여러 원천 행을 객체 하나로 모으므로(`collect`),
  바뀐 행만 넣으면 모은 값이 일부만 남는다. `sp_table` 은 같은 입력이면 같은 결과라 출력끼리의
  비교가 맞는다. *보강(2026-11-06)* — 전체를 하되 **메모리에 통째로 들지 않는다**: 타입마다 식별자의
  해시로 행을 바구니에 나눠 틀의 모으기를 바구니마다 부르고(같은 식별자의 행은 한 바구니), 비교도
  같은 식으로 나눈다. 결과는 틀의 변환기 · 한꺼번에 한 비교와 바이트까지 같다(`relay_core/table.py`
  · `diff.py`, 시험이 묶는다). 원천이 커도 실행의 메모리는 바구니 하나 몫이다.
- **비교의 기준은 「적용된 것」 이다.** 계획이 대기 중인 채 다음 실행이 돌면 적용된 기준과 다시 견줘
  대기 계획을 대신한다 — 파이프라인마다 대기 계획은 하나다.
- *보강(2026-11-07)* — 설계는 AI 만의 일이 아니다: 화면의 **새 연결**로 사람이 원천의 주소 · 모양을 받아 정의 판 ·
  레시피 판 초안까지 짓는다(MCP 클라이언트가 없는 자리에서도 본업이 막히지 않게). 사용은 여전히 사람이 상세에서.
- **AI 의 자리는 설계 때다.** MCP 로 붙은 AI(Claude · 사내 GLM)가 원천 표본과 대상 정의를 읽고 레시피
  초안을 저장하고, 미러에 시험해 보고서를 읽고 고친다. **켜는 것은 사람이 화면에서** 한다(MCP 에
  켜는 도구가 없다). 보고서는 값을 가린 패턴(`A` · `9` · `가`)이라 사외 AI 에도 원본 값이 안 나간다
  — 다만 열 이름 · 코드 목록은 남으므로 그 반출은 정책을 확인한다.
- **실행 중의 LLM 은 남은 것만.** 운영은 B300 의 GLM, 개발은 Ollama — OpenAI 호환 클라이언트 하나로
  설정만 다르다. key 는 대상에 있는 후보 안에서만 고르고, 출력은 JSON 스키마로 강제하고, 확신도가
  모자라면 보내지 않는다. 승인된 판정은 레시피의 사전으로 올라간다.
  *보강(2026-11-07)* — 실행 중에 LLM 이 혼자 정하지 않는다: 미해결은 미해결로 멈추고, **미해결 작업함**에서
  사람이 대상의 후보(규칙 · 대상 · GLM 의 제안) 중 키를 선택한다. 승인한 대응은 두 곳으로 간다 — 레시피 판의
  **relay 사전**(`relay_aliases` — 틀이 대상의 별칭 · 이름 풀이를 받아 두는 자리에 끼운다. 대상의 판정이 먼저,
  대상에 없는 키는 쓰지 않는다)과, 같은 목록의 **별칭 요청 목록**(대표 플랫폼에 별칭 등록을 요청하는 CSV). 기준정보와
  그 별칭은 대표 플랫폼의 것이라 relay 는 만들지 않는다 — 대표 플랫폼에 등록돼 퍼지면 relay 사전의 그 줄은 쓰이지
  않는다. 틀의 레시피 문법(`map`)으로는 값 하나만 다른 키로 보낼 수 없어서(칸에 `map` 이 있으면 참조 대조까지 가지
  않는다) 이 칸을 두었다.

### 3. SP 틀을 포크한다 — 온톨로지 · 데이터 소스 · 웹훅은 빼고

화면(연결 지도)이 필요하고, 화면이 생기면 로그인 · 권한 · 감사 · 실패 알림 · 작업 워커 · 배포가 함께
필요하다. 전부 SP 틀에 있다. SimEngBay 와 같은 방식으로 **최신(v0.4.72)에서 포크하고 걷어냈다.**

- 가져온 것: 계정 · 인증(PAT · HWAX 포털) · 부서 · 공지 · 알림 · 감사 · 첨부 · **작업 워커** · 서버 상태 ·
  확장 기제 · Apptainer 배포.
- 걷어낸 것: 온톨로지 · 객체 · 지식 그래프 · RDF · 검색 · 지표 · 검토함 · 장표 · 게시판 · 웹훅 · 데이터
  소스 · 묶음 · 코어 API · 뜻으로 찾기(pgvector) · MCP 서버 · 정제 도구 폴더, 확장 `caegroup` ·
  `jajuverify`. 마이그레이션은 모델에서 다시 만든 `0001_initial` 하나로 시작한다.
- 이름: slug `datarelay`, 화면 이름 「데이터 중계」, 오류 접두사 `DRL`, 포트 **8080 / 8081 / 8082**,
  Vite 5250. PAT 쓰기 범위는 `relay:write` 하나.
- 틀의 개선은 자동으로 못 받는다. 인증 · 배포는 안정된 부분이라 갈라져도 비용이 작다 — 필요한 것은
  골라서 옮긴다. 틀의 문서와 ADR 은 [docs/sp/](../sp/) 에 v0.4.72 시점 그대로 두었다 — **코드 주석의
  ADR 번호가 틀에서 온 주석이면 그 번호다.**

### 4. 엔진은 순수 패키지 — `backend/relay_core/`

DB 도 웹도 모른다(MatNexus 의 `matcore` 자리). CLI(`relay run`)와 화면의 「지금 실행」(작업 워커)이
같은 함수를 부른다. `app` 을 import 하지 않는다 — 시험이 지킨다.

### 5. SP 도구는 흡수하지 않는다 — 판을 고정한 사본

`sp_pipeline.py` · `sp_table.py` 는 SP 에 두고, 이 저장소는 `vendor/sp_pipeline/` 에 **판을 고정한
사본**을 둔다(`VERSION` 에 태그 · 커밋 · 해시, `scripts/sync_sp_pipeline.sh`). 사본은 고치지 않는다.

흡수(옮기기)하지 않는 까닭:

- SP 의 백엔드 시험(`tests/api/test_pipeline_cli.py` 등)이 그 도구를 **실제 앱에 돌려** 묶음 · 작업 API
  와 함께 지킨다. 옮기면 SP 가 API 를 바꿔도 SP 의 CI 는 모르고, relay 가 새벽에 깨진 뒤에야 안다.
- SP 릴리스가 판마다 PC 키트(`sp-pipeline-<판>.zip`)를 내고, 그룹이 자기 문서 · 엑셀을 정제하는 길은
  계속 그 키트다 — **공유 원천(PLM · MES)은 relay 에서 한 번, 플랫폼 고유 원천은 그 플랫폼에서.**
- relay 에 필요한 것은 도구를 고치는 것이 아니라 그 앞뒤(받기 · 미러 · 비교 · 무덤 · 일정 · 제출)다.

흡수가 맞아지는 날: PC 키트 길을 닫고 모든 적재를 relay 로 모으기로 할 때. 그때 두 도구를 옮기고 SP
시험이 relay 의 판을 부르게 바꾼다.

**흡수하는 것은 레시피와 운영이다.** 지금 SP 의 사내 폴더(`docs/사내/plm/`)에 있는 PLM 대응 파일
(`plm-models.table.json` · `plm-ontology.json`)이 첫 레시피다. 레시피는 열 이름 · 코드 체계가 사내
정보라 저장소에 넣지 않고 DB 에 판으로 둔다(초안 · 활성 · 되돌리기 · 감사), 파일은 내보내기 형식.

### 6. 화면 — 연결 지도가 첫 화면

열을 고정한 흐름도: **원천 시스템 → API → 파이프라인 → 대상 SP → 타입.** 정의(파이프라인 · 레시피 ·
대상 스키마 스냅샷)에서 매번 계산하고 손으로 그리지 않는다. 색은 상태(정상 · 적용 대기 · 실패 ·
멈춤), 선 굵기는 지난 실행의 건수. Datahub 너머(코어 현황의 수신자)를 회색으로 이어 그린다.
파이프라인 상세(칸 대응 표 · 실행 이력) · 거꾸로 보기(이 값은 어디서 왔나) · 대상 인스턴스 · 원천
시스템이 뒤따른다. 1차는 읽기 전용 + 「지금 실행」, 화면 편집은 2차. 보는 것은 로그인한 사람, 실행 ·
적용은 시스템 관리자.

## 대안

| 대안 | 기각한 까닭 |
| --- | --- |
| 각 플랫폼이 지금 방식(AI 가 매번 가공)을 자동화 | 매 실행 AI — 결과가 갈리고 느리고 사람이 붙는다. 공유 원천을 플랫폼마다 받으면 PLM 접속이 늘고 허브 배포 구조가 깨진다 |
| SP 데이터 소스를 키워 허브가 스스로 당긴다 | SP 코어에 원천별 사정(인증 · 중간 시스템 · LLM)이 들어간다 — SP ADR 0001(도메인은 코어에 없다)과 부딪히고, 원천이 바뀔 때마다 모든 인스턴스를 다시 배포한다. 매핑 문법도 둘(데이터 소스 · `sp-table/1`)이 된다 |
| 화면 없는 수집기만 | 「어떤 플랫폼의 어떤 API 가 어떤 SP 에 어떻게」 를 한눈에 볼 자리가 없다(사용자 요구, 2026-11-05) |
| 별도 표준 모델(Canonical Data Model)을 둔다 | 표준은 이미 대상 SP 의 온톨로지와 `sp-bundle/1` 이다. 중간 스키마를 두면 정본이 둘이 되고 갈린다 |
| Temporal · Redis · RabbitMQ | SP 틀에 Postgres 작업 워커(계획 → 확정 → 적용 · 진행률 · 취소 · 되살리기 · 이중 서버)가 있다. 폐쇄망 · SIF 하나 배포에 엔진을 늘릴 까닭이 없다 |

## 결과

- 지금 PC 에서 손으로 하던 「PLM API → AI 가공 → sp_pipeline」 을 서버가 매일 규칙으로 돌리고, 그
  상태를 화면이 보여 준다.
- 백엔드 시험 269 · 프론트 시험 215(포크 직후, 2026-11-05).
- 틀에서 그대로 들고 온 배포 스크립트는 아직 MCP · 동기화 · 지표 분기를 품고 있다(파일이 없으면
  건너뛴다). `build_bundle.sh` 는 `vendor/` · `relay_core/` 를 담도록 고쳐야 한다 — 배포 단계에서.
