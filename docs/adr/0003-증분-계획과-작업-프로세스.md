# 0003. 증분 계획과 작업 프로세스 — 바뀐 행이 닿는 객체만, 작업마다 따로

- 상태: 채택
- 날짜: 2026-11-25
- 관련: [ADR 0001](0001-허브-앞단의-중계-플랫폼.md) §2(변환은 늘 미러 전체 — 이 결정이 바꾼다), `backend/relay_core/incremental.py` ·
  `isolate.py` · `memory.py`, `docs/개발계획.md` 「큰 미러의 실행」

## 배경

실행마다 받은 양과 상관없이 미러 전체를 변환하고 적용된 출력 전체와 비교했다. 하루 1~2만 행이 와도 58만 행을 다시
계산한다. 작업은 워커 프로세스 안에서 돌아, 큰 실행이 쓴 메모리가 끝난 뒤에도 워커에 남고, 메모리가 모자라면 같은
서버의 datahub 까지 위험했다. 어느 단계가 메모리를 쓰는지 잰 기록도 없었다.

요청(2026-11-25): 단계별 메모리를 기록하고, 작업마다 프로세스를 나누고 상한을 두며, 이번에 받은 행이 닿는 객체만 다시
변환 · 비교한다. 조건은 셋 — **증분 결과가 전체 결과와 바이트 단위로 같다**, 224만 행 미러의 하루치 실행이 58만 행
전체 실행보다 메모리를 적게 쓴다, 수신 검증 · 분할 번들 · 회수 · 대조는 지금처럼 동작한다.

## 결정

### 1. 바뀐 모으기만 다시 모아 지난 출력에 끼운다

객체 하나는 그 타입의 식별자가 같은 행들과 참조 대조의 답에만 달려 있다(선은 출발점이 같은 행들). 그래서 바뀐 행의
**옛 식별자와 새 식별자**를 가진 미러의 행 **전부**를 다시 모은다. 값 충돌 검사도 그 안에서 지금처럼 한다. 나머지는
지난 변환의 출력에서 옮기고 행 번호(`_source.row`)만 다시 매긴다(미러는 키 차례라 남은 행의 앞뒤가 같다).

- **참조가 나중에 채워지는 것을 지킨다.** 이미 본 참조 표기(서로 다른 값)를 실행마다 지금 대상으로 다시 풀고, 답이 바뀐
  표기를 가진 행도 다시 모은다. 바뀐 행이 하나도 없어도 대상에 식별자가 생기면 다음 계획에서 채워진다. 처음 보는 표기는
  전체 변환과 같은 규칙으로 대상에 묻는다.
- **비교도 건드린 것만.** 지난 출력이 기준(적용된 것)이면 다시 모은 것만, 적용을 기다리는 동안 여러 번 돌면 **기준과
  다를 수 있는 앞 값과 기준에 있던 그 줄**을 실행 옆(`work/<때>.base`)에 이어 적어 그것만 견준다.
- **색인**은 파이프라인마다 SQLite 하나(`work/<파이프라인>/incremental.sqlite`)다. 전체 변환이 짓고 증분이 트랜잭션 하나로
  이어 쓴다. 백업에는 넣지 않는다 — 없으면 전체로 다시 짓는다.

### 2. 의심스러우면 전체로

증분은 빠르게 할 뿐이다. 아래는 모두 전체 변환으로 가고 **까닭을 실행 추이에 적는다**.

- 색인이 없음, 색인이 본 미러가 지금 미러와 다름(미러를 반영한 뒤 변환이 멈췄거나 미러를 백업에서 되돌림), 색인을 이어
  쓰다 중단됨.
- 레시피 · 계산 필드 · 온톨로지 · **변환 코드**가 바뀜 — 새 버전을 설치한 뒤 첫 실행은 전체다(옛 코드의 출력에 이어
  붙이지 않는다).
- 되풀이할 수 없는 레시피 — 해석기(`parser`), `on_missing: unresolved`, 식별자 · 이름 · 관계 속성의 대상 참조 대조.
- 바뀐 행이 10만 건을 넘음, 옮긴 객체 수가 헤아린 수와 어긋남, 그 밖의 오류.

### 3. 작업마다 새 프로세스

실행 · 적용 · 대조 · 회수를 새 프로세스에서 돌린다(`relay_core.isolate` — 엔진만 불러온다). 워커가 정의 · 인증 정보를 풀어 넘기고 결과만
받는다. 끝나면 메모리가 운영체제로 돌아간다. `RELAY_JOB_MEMORY_MB` 를 두면 워커가 자식의 RSS 를 보다 넘으면 그 프로세스만
끝내고 작업을 실패로 적는다(단계와 최고치도). 자식은 `oom_score_adj=1000` 이라 상한을 두지 않아도 운영체제가 datahub
대신 이 작업을 먼저 끝낸다.

### 4. 재는 것을 먼저

단계마다 최고 RSS(`/proc/self/clear_refs` 로 최고치를 되돌려 정확히)와 시간을 실행 추이에 남긴다. 효과를 이 기록과
`devtools/bench/relay_scale.py` 로 쟀다(결과는 개발계획).

## 대안

- **객체 저장소를 따로 둔다(타입마다 행을 DB 로).** 옮길 것을 파일에서 읽지 않아도 되지만, 출력 폴더가 정본이 아니게
  되고 바이트 동일을 지키기 어렵다. 지금의 폴더 · 묶음 · 대조 · 회수가 모두 출력 폴더를 읽는다.
- **비교만 증분으로.** 변환이 시간의 대부분이라 효과가 적다.
- **cgroup 으로 상한을 건다.** 컨테이너(Apptainer)와 이중화 노드마다 권한이 달라 설치가 복잡해진다. 프로세스의 RSS 를 보는
  것으로 충분하고, 넘었을 때 어느 단계였는지 적을 수 있다.

## 결과

- 하루치 실행의 메모리는 미러 크기를 거의 따르지 않는다(바뀐 행 · 닿은 객체를 따른다). 시간은 미러를 한 번 훑는 몫만
  미러 크기를 따른다.
- 디스크에 색인이 더 든다(224만 행에 약 360MB).
- 레시피를 바꾼 날 · 새 버전을 설치한 날은 전체 변환이라 메모리 · 시간이 예전과 같다. 상한은 그날을 보고 정한다.
- **증분 변환을 고칠 때**: `tests/unit/test_relay_incremental.py` 가 무작위 미러 · 변경 · 대상 식별자 · 별칭에서 출력 폴더 · 보낼
  폴더 · 색인을 전체와 바이트로 견준다. 변환(`table.py`)의 규칙을 고치면 이 시험이 먼저 말한다.
